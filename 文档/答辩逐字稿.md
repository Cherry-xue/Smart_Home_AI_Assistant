## 0:00–0:45　开场

各位老师上午好，我是 XXX，我的毕业设计题目是《基于多 Agent 协作的智能家居 AI 助手设计与实现》。

先用一句话说清楚它是什么：**它不是"一个大模型加一堆设备接口"，而是让 5 个各有分工、各有权限边界的 Agent 并行工作，再由一条确定性的主干把它们的结论收敛成可执行的动作；而涉及门锁、燃气这些危险动作，代码里根本不存在自动执行的通道。**

今天我会用一半时间讲 Agent 是怎么设计的，另一半讲这套东西怎么保证不骗人、不乱动。

---

## 0:45–2:15　选题与三条硬约束（1.5 分钟）

先说为什么做这个题。

市面上的智能家居助手，大多是一问一答：你问"客厅多少度"，它查一下告诉你。但真实的家庭场景不是这样的——用户说"我出门了"，背后其实同时涉及关灯、关空调、检查燃气阀、布防四件事，这四件事属于四个不同领域，需要不同的数据和不同的判断。

所以我的思路是：**把"一个全能助手"拆成"一个协调者加五个专家"**，让专业的事交给专业的 Agent，协调者只负责分派和汇总。

但真正决定这套系统长什么样的，是**三条硬约束**，我先交代清楚，后面所有设计都是围着它们转的。

**第一条：我没有真实设备。** 数据全来自我自己写的生成器。所以每条数据都带来源和质量标记，前端明确标注"模拟"，**不能把模拟数据伪装成实测值**。

**第二条：后端连数据库的账号没有建表权限。** 只有一个增删改查账号。这就逼出了两个设计：新增字段只能塞进已有的 JSON 列；户型图这种新东西干脆不落库，存成文件。

**第三条，也是最关键的一条：门锁、燃气阀、电气总闸、布防撤防这四类设备，绝不自动执行。** 注意我的措辞是"绝不自动执行"，不是"批了也不执行"——人工批准之后，它会**真的下发一次**。这条线怎么在代码里守住，是我今天要重点讲的。

---

## 2:15–3:45　系统总览（1.5 分钟）

【切换到大屏总览页】

整个系统跑在四个进程上：MQTT Broker、数据生成器、FastAPI 后端、前端大屏。

数据从生成器发布到 Broker，后端起一个订阅线程落库；前端只跟后端说话，通过 Vite 代理走同源。

这里有一个我踩过的坑值得说：**Windows 上 MQTT 客户端库要求 Selector 事件循环，而 uvicorn 默认用 Proactor，而且事件循环一旦创建就不能改类型。** 所以我把订阅放进了独立线程，线程自带循环，跟 uvicorn 用什么循环完全无关；同时它还在同一个进程里，跟 API **共享同一份设备目录和最新值缓存**——如果拆成两个进程，就会变成"一边写、一边读"，接口永远读不到实时值。

技术栈是 FastAPI 加同步 SQLAlchemy、MySQL 8、LangGraph、Vue 3。我**刻意没有引入** Redis、Celery——单机场景它们只增加运维面，不增加能力。

规模上，纯程序代码三万行，后端一万六千多行，数据库 25 张表、218 个字段，41 个 API 端点。

## 3:45–9:45　**重点：Agent 是怎么设计的**（6 分钟）

下面进入今天的重点。

### 3:45–4:45　为什么手写图，而不是一把梭

LangChain 提供了一个很方便的东西，叫 `create_react_agent`：给它模型、给它工具，它自己就会思考该调哪个工具。我一开始也这么写，但很快发现三个问题。

**第一，它的流程是黑盒。** 用户问"我出门了"，它到底调了哪几个工具、为什么这么调，我拿不到结构化信息，前端也就没法显示"系统正在做什么"。

**第二，它没有"停下来等人"的位置。** 而我的场景里，开锁这种动作必须停在半路等人批准。

**第三，它没法并行。** 关灯、关空调、查燃气是三件互不依赖的事，串行做就是白白多等两倍时间。

所以我改成了手写 `StateGraph`：**拓扑我自己定，每个节点干什么我自己写，模型只负责在自己那一段里做判断。** 这就是我的第一个设计原则——**能用确定性代码表达的东西，不要交给模型。**

### 4:45–5:45　图长什么样

【切换到系统状态页，或直接指架构图】

整张图是十二个节点，分四段。

**第一段是路由。** 一个轻量模型调用，判断这句话该交给哪几个专家，输出一份结构化结论：激活哪几个 Agent、为什么、要不要先反问用户。

**第二段是并行扇出。** 路由结论里有几个 Agent，就用 LangGraph 的 `Send` 扇出几路，它们**同时跑**。五个专家是：场景编排、安防应急、能源优化、照护、通用助手。

这里有个细节：并行分支的结果要合并，所以我给 `findings` 和 `trace` 两个通道声明了累加式的 reducer，多路同时写会逐条累加而不是互相覆盖；而路由结论、执行计划这些"只有一个节点会写"的通道，我**故意不加** reducer，加了反而会在重跑时叠加出脏数据。

**第三段是确定性主干。** 五个专家的结论汇总之后，进入计划节点：做能力校验、量程校验、冲突检测——比如两个专家一个说开灯一个说关灯，这里就会被抓出来做成一个待裁决项。然后低风险动作直接执行，高风险动作进确认节点。

**第四段是回答。** 把事实、分析、待确认项分区返回，同时把每个节点的执行痕迹一起带出去，前端"已完成 5 步 / 查看执行过程"就是读这个。

最后还有一个工程细节：`create_agent` 每创建一个要 0.9 秒，五个就是 4.5 秒。所以我按"设备目录 + 套房"做了进程级缓存，否则每次请求都要多等四五秒。

### 5:45–7:15　权限表：每个 Agent 能碰什么

这是我认为整个设计里最值得讲的一点。

五个 Agent 不是"都给全部工具、靠提示词约束"——**每个 Agent 有一张工具白名单，写在代码里，是一张权限表。**

比如场景编排 Agent，它能读设备状态、能查能力、能查预置意图、能检索说明书，但它**不能下发指令**；安防 Agent 能读最近事件、能查应急预案，但它**同样不能开锁**；能源 Agent 能读历史、能算电费、能查电价；照护 Agent 能读活动节律、能查长期记忆。

而最关键的是：**工具层里根本没有"执行"这个工具。** 我在构建工具的时候写了一个断言，一旦有人往工具列表里塞下发通道，启动就会失败。

所以我的红线不是靠提示词说"请不要开门"，而是**靠代码结构上根本没有这条路**。这是第二个原则——**安全要靠架构保证，不要靠模型的自觉。**

### 7:15–8:30　人机协同：怎么停下来、怎么恢复

高风险动作会走到确认节点，这时用 LangGraph 的 `interrupt()` 把图暂停，把待确认项推给前端；用户批准后，用 `Command(resume)` 从暂停的地方继续。

这里面有两个坑我都踩过。

**第一个坑：中断之后数据库里什么都没有。** 早期版本是"等批准了再落库"，结果暂停期间进程只要重启，待确认项就消失了，用户看到一个提示说有，但列表里找不到。后来我改成**生成待确认项的那一刻就落一条 `pending_confirm` 记录**，把指令 id 回填到待确认项上。这样列表可以从数据库重建，批准就是更新那一行，而不是再插一条。

**第二个坑：恢复会把被中断的节点整段重跑。** 这意味着节点里写数据库的代码必须**幂等**。我的做法是按"会话 + 设备 + 能力"复用已有的一行，日志里能看到"复用已存在的待确认指令"这句话。

恢复之后，风险动作交给一个函数：全项目**唯一**允许高危设备动起来的函数。它只被两个地方调用——面板上手动下发的批准、Agent 编排里的批准。自动路径永远走不到它，因为执行器一遇到高危设备就直接跳过，只写一条待确认。

状态链是四步：待确认、已确认、已执行，驳回则作废。中间"已确认"那一步是故意留的痕迹——能看出"人批了但没发出去"。

### 8:30–9:15　记忆与知识

Agent 还有两块"外挂"。

一块是**长期记忆**：成员偏好、说过的话、家里发生过什么，存在记忆表里，照护和通用助手可以检索。

另一块是**知识库**：六份设备说明书和家庭应急预案，切块后用千问的向量模型入库，检索时先向量召回再用重排模型精排，**每一条命中都带出处**，能指到是哪份文档的哪一节。所以回答"燃气报警了怎么办"时，它引用的是我写的应急预案，而不是自己编。

### 9:15–9:45　一个真实案例

【切换到对话页，或直接口述】

举个真实跑通的例子。我说"帮我把入户门锁打开"。

路由判定为场景编排；专家读设备状态，发现门锁是锁着的；计划节点识别出这是一台高风险设备；确认节点暂停，落一条待确认记录；我在列表里点"批准并下发"；这时才真正发出一条 MQTT 指令；模拟器收到后执行并回执；门锁状态从 locked 变成 unlocked，前端才显示已开锁。

**整个过程里，模型只提了建议，动的是人。**

## 9:45–11:45　工程与质量（2 分钟）

这套东西我写了三万行，怎么证明它是对的？

我做了 **12 个验收脚本、698 项断言**，每次改完代码全跑一遍。它们不是单元测试，是**验收**——比如有一个脚本专门校验"ORM 定义和数据库"是否完全一致：25 张表、218 个字段，表名、字段名、类型、可空性、主键，一个都不能差，因为我没有建表权限，一旦不一致只能靠它发现。

还有一个脚本做**前后端契约对账**：前端用到的每个端点必须在 OpenAPI 里存在，依赖的每个字段必须在真实响应里存在。这个脚本抓到过一个很隐蔽的 bug——设备总数的字段叫 `total` 不是 `devices`，写错了页面不报错，只是设备数永远显示 0。

另外有一个脚本专门守红线：全库断言"凡是已执行的指令，必须有确认时间"，防止有人绕开确认直接执行。

除了脚本，我还做了手工闭环实测：面板下发、批准、设备状态真的变了；驳回，状态纹丝不动；连点三次"解锁"，待确认项只留最新一条——**这条也是测出来的 bug**：库里旧的已经作废了，但内存索引没同步清，界面会列出三条一样的待办，其中两条点了只会回"已处理过"。

## 11:45–13:45　难点与取舍（2 分钟）

讲三个我认为最有价值的难点。

**第一，时间语义。** 一条数据有三个时间：设备观测时间、本机收到时间、最新观测时间。判设备在不在线**必须用收到时间**，因为设备时钟可能不准，补发的旧数据时间还可能是"过去"。另外我的模拟器是倍速跑的，数据时间可能不在"现在"附近，所以前端所有缺省时间窗都以"数据锚点"为基准，否则页面会一片空白。

**第二，多套房隔离。** 家里可以有多套房，每套有自己的户型、设备、数据。这里的坑是：**任何"会挑设备的代码"都必须先把设备目录按套房收窄。** 我把收窄做在目录这一层，而不是给每个查询加参数——因为编排链路全程只认目录，改一处就全生效，也不会漏掉某一条路径。漏一条的后果就是"在 2 号房点按钮，动作落在 1 号房设备上"。

**第三，把"没有建表权限"从限制变成了设计。** 场景收藏塞进场景定义的 JSON 列，户型几何存成文件。听起来是妥协，但户型数据能随项目走版本管理，改坏了直接还原。

---

## 13:45–15:00　总结与展望（1 分钟）

最后总结。

这套系统完成了什么：一套可运行的智能家居后端加大屏，五个专业 Agent 并行协作，长期记忆加知识库检索，以及一条**用代码结构守住的高危动作人工授权链**。所有能力都有验收脚本和手工实测兜底。

没完成什么，我也说清楚：**手机端还没做**；**批量评测还没做**——我计划用 50 到 100 条问答用例，量化意图准确率、动作正确率和幻觉率；**容器化编排也还没做**。这三项是我下一阶段的目标。

如果只用一句话概括我的设计观：**模型负责理解和建议，代码负责边界和执行。**

我的汇报到这里，请各位老师批评指正。

# 附录 B：可能被问到的问题（备答要点，不念）

| 问题 | 回答要点 |
|---|---|
| **为什么不用现成的 Agent 框架/工作流平台？** | 试过 `create_react_agent`，但拿不到结构化过程、没有暂停位、不能并行。手写 StateGraph 换来的是可审计、可单测、可扩展——加第六个专家只改一个常量和一个条件边。 |
| **5 个 Agent 是不是过度设计？一个模型加工具不行吗？** | 单 Agent 的问题不是能力不够，是**权限收不住**：一个能开锁的 Agent，也可能在无关场景里误开锁。拆开之后每个 Agent 的工具白名单是硬边界。而且并行确实快。 |
| **大模型会不会乱调工具？** | 它只能在白名单里调；白名单里没有执行类工具；高危动作即使被"提议"，也必须经过确定性计划和人工确认。 |
| **幻觉怎么控制？** | 三个手段：温度设 0；知识类问题必须走检索且带出处；数据不足时不给确定性金额、不做医疗断言——这是写进规则的，不是靠提示。 |
| **中断之后进程挂了怎么办？** | 待确认项在中断前就落库了，列表可以从库里重建；如果配 MySQL checkpointer，恢复现场也能跨重启。 |
| **为什么用同步 SQLAlchemy？高并发怎么办？** | 单机单用户，同步更简单；查询端点都写成同步函数，不阻塞事件循环。真要上并发，先换异步驱动，接口层不用动。 |
| **高危设备的"批准"会不会被脚本绕过？** | 全项目只有一个函数能执行高危指令，只被两个入口调用；自动路径执行器遇到高危直接 `continue`；库里还有全库断言"已执行必有确认时间"。 |
| **数据都是假的，这个项目有什么意义？** | 数据生成器是按物理模型写的（温度惯性、功率曲线、故障注入），而且数据源是可插拔的：改成真实网关只需换 `DATA_MODE`，上层业务代码一行不动。 |
| **为什么前端不用 TypeScript？** | 8 个页面、单人开发，收益不足以抵消成本；替代方案是"字段只在 api 层定义一处"加契约对账脚本，把类型错误变成可检测的字段缺失。 |
| **三万行里有多少是自己写的？** | 代码量与架构说明书的统计口径一致：纯程序代码三万行，其中后端一万六、前端一万、模拟器一千八、脚本九百；验收脚本另有四千行。 |
| **如果给你更多时间，最先做什么？** | 批量评测。现在能力是"能跑通"，但缺量化指标；有了 50 到 100 条用例，才能说清楚意图准确率和动作正确率是多少。 |
