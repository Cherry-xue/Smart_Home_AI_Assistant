## 2. 四项已定决策的展开

### 2.1 大模型：DashScope 云端 API

- **接口形态**：`langchain_openai.ChatOpenAI` 指向**百炼兼容端点**——这与 `资料/02_LangChain 核心组件.md` 里课程代码的写法**逐字一致**：

```python
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    api_key=os.getenv("DASHSCOPE_API_KEY"),
    base_url=os.getenv("DASHSCOPE_BASE_URL"),   # https://dashscope.aliyuncs.com/compatible-mode/v1
    model=os.getenv("QWEN_MODEL_NAME"),         # qwen-turbo
    temperature=0,          # 设备控制要确定性，不要创意
)
```

- **模型选择：`qwen-plus`**（v1.2 遵从用户决定保留 turbo；v1.3 因 turbo 已下架而改为 plus）。
  - **决策依据**：用户确认其 RAG 项目曾可正常使用 `qwen-turbo`，说明不是用法问题；结合实测（`qwen-turbo` → 429，`qwen-turbo-2024-11-01` → **403 `access_denied`**，`qwen-turbo-0919` → 404 已下线），判断为**该模型已下架或不再对本账号开通**。
  - **`qwen-plus` 当前有免费额度**，实测 HTTP 200 可用，且多步任务拆解质量明显优于 turbo——对"高风险拦截率 100%"这个硬指标是加分项。
  - `.env` 里保留了 `# QWEN_MODEL_NAME=qwen-turbo` 的注释行备查，将来若 turbo 恢复开通可直接切回。
- **为什么不用本地模型**：4GB 显存只能承载 1.5B~3B 量化模型，会让"高风险拦截率 100%"的硬指标失守。
- **代价与对策**：
  - 断网不可用 → 界面上明确显示"模型服务不可用"，且**设备监控与手动控制必须仍可用**（规划书第 17 章）；架构上要做到模型调用失败不阻塞 REST 查询。
  - 有 API 成本 → `temperature=0`、`ModelCallLimitMiddleware(max_calls=8)`、`trim_messages` 截窗口、同类查询结果缓存。
  - **遇 429/403 要有降级**：模型调用要显式处理 `limit_requests` 与 `access_denied`，前端提示"模型配额不足"，而不是抛 500。
- **Embedding**：`qwen3.7-text-embedding`——**已实测可用，向量维度 1024**。既有 RAG 项目用的也是它（`EMBEDDING_TEXT_LENGTH=2048`、`EMBEDDING_BATCH_SIZE=10`），沿用可让两个项目向量空间一致、经验复用。
  - LangChain 侧的取法有两条，安装后**实测选一条**：`OpenAIEmbeddings` 走 compatible-mode，或 `DashScopeEmbeddings`。
  - **灌库是一次性大额调用**，嵌入结果必须落到 `chroma_db/` 持久化目录，进程/容器重建不要重跑。
- **重排（rerank）**：用户指定的 `qwen3-rerank` **在百炼模型列表中不存在**，实际 ID 是 **`qwen3.7-text-rerank`**（rerank 类目下仅此一个），已按实际 ID 写入 `.env`。
  - ⚠️ **rerank 不走 OpenAI 兼容协议**，需要 `dashscope` 原生 SDK 或 DashScope 原生 REST 端点，因此依赖清单里要单独加 `dashscope` 包（见 §6.1）。
  - 首期说明书数量少，rerank 属**可选优化**；启用时机是"检索结果明显串味"时，而不是现在就上。
- **Tavily（可选）**：`.env` 里的 `TAVILY_API_KEY` 可用来补"外部服务数据"（天气、空气质量），正好对上需求分析 §3 的"外部服务数据"一环。首期非必需。

### 2.2 部署：本地直跑

- 后端 `uvicorn --reload`，前端 `vite dev`，**Mosquitto 装成 Windows 本机服务**；**MySQL 不装本机**，直连虚拟机 `192.168.159.100:3306`。
- **保留 Compose 不写进首期**，但把 §7 的目录结构按"将来能加 Dockerfile"的方式摆好——等答辩/交付需要"一键起服"时，补 `Dockerfile` + `docker-compose.yml` 即可，不需要重构代码。
- **唯一要守住的纪律**：所有连接地址从环境变量读（`DATABASE_URL` / `MQTT_HOST`），**代码里绝不出现 `127.0.0.1` 硬编码**。这是规划书第 15 章点名的坑，本地直跑阶段最容易犯。

### 2.3 数据来源：保留 MQTT 虚拟设备

用户已明确"可以用 MQTTX 模拟输入，可以制作一个数据生成器"，因此保留 MQTT 链路，但**它的定位从"边缘网关接入"下调为"开发期数据源"**：

```text
                    ┌───────────────────────────────┐
  MQTTX 手工注入 ───▶│                               │
                    │   Mosquitto 2.x（本机 1883）   │
  自研数据生成器 ───▶│                               │
                    └───────────────┬───────────────┘
                                    │ 订阅（aiomqtt，async）
                                    ▼
                          FastAPI 后端
                     ┌──────────────┴──────────────┐
                     │ 落库：device_readings        │
                     │      energy_readings         │
                     │      sensor_events           │
                     │ 缓存最新值（内存 + DB）      │
                     └──────────────────────────────┘
```

- **为什么保留 MQTT 而不是直接写库**：① 它把"设备"和"平台"真正解耦，将来换真机只改 topic 与适配器；② 你可以用 MQTTX 随时随地手工注入一条"燃气泄漏"来演示，不用改代码；③ 答辩时"云边端协同 + 协议抽象"这条创新点才有实物可讲；
- **为什么用 aiomqtt 而非 paho-mqtt**：后端是 async 的，`paho` 的 `publish/loop` 是阻塞调用，直接用在 `async def` 里会卡住整个事件循环（规划书 §12.5 已点明）。**数据生成器是独立进程，用 paho 无所谓**，反而更简单。

**Broker 与客户端勘查结论（v1.3 新增，基于本机实测）**

| 项 | 勘查结果 | 结论 |
|---|---|---|
| `D:\Code\单片机\mqtt\mqttfx.exe` | **MQTT.fx** 的 install4j 启动器，自带 JRE 8，纯 **GUI 客户端** | ✅ 可用作"手工注入/观察报文"的工具；**它不能当 broker** |
| 本机是否有 broker | `Program Files`、`Program Files (x86)`、`D:\soft` 均无 mosquitto / EMQX / nanomq | ❌ 没有，需要选一个 |
| 用户既有 MQTT 用途 | 单片机项目连的是**阿里云 IoT**（`*.iot-as-mqtt.cn-shanghai.aliyuncs.com`）与**移动 OneNET**（`mqtts.heclouds.com`） | 这两个都要设备三元组鉴权，**不适合当开发环境** |
| 公共测试 broker 可达性 | `broker.emqx.io:1883`、`test.mosquitto.org:1883`、`broker.hivemq.com:1883` **三者 TCP 连通且 MQTT 握手均返回 `20020000`（CONNACK 成功）** | ✅ 零安装方案可行，可立即开测 |

**两条路，建议 A 为主、B 为辅**（**v1.5 更新：方案 A 已落地** —— conda-forge 装了 Mosquitto 2.0.15，免管理员，详见 §12.6）：

- **方案 A（推荐）：本机装 Mosquitto 2.x** —— 只需把 `mosquitto.conf` 配成监听 `1883` 且允许本地匿名连接，MQTT.fx 与我们的生成器都能连。数据全在本机，演示时不受网络影响。
- **方案 B（零安装，可立刻验证）：指向公共 broker** —— 把 `.env` 的 `MQTT_HOST` 改成 `broker.emqx.io` 即可。选 **EMQX 公共 broker 的额外好处：与你的 MQTT.fx 是同一家，客户端里自带该连接配置，不用手填**。
  - ⚠️ 公共 broker 是**公网明文、任何人可订阅**，只允许发模拟数据，**绝不发真实家庭数据**；topic 里要带一个随机前缀避免与陌生人撞名。
  - 这条路的定位是"今天就想看到数据流"的过渡手段，正式联调仍应回到方案 A。

**Topic 契约**（建议现在就冻结，前端/模拟器/后端都按它来）：

```text
smart_home/{home_id}/room/{room_code}/device/{device_code}/state      # 设备状态（retained, QoS1）
smart_home/{home_id}/room/{room_code}/device/{device_code}/telemetry  # 高频遥测（QoS0）
smart_home/{home_id}/room/{room_code}/device/{device_code}/event      # 事件（水浸/烟感/门窗, QoS1）
smart_home/{home_id}/room/{room_code}/device/{device_code}/cmd        # 指令下行（后端→设备, QoS1）
smart_home/{home_id}/room/{room_code}/device/{device_code}/cmd_ack    # 指令回执（QoS1）
smart_home/{home_id}/system/heartbeat                                 # 网关心跳
```

**统一消息信封**（所有 topic 共用一个 payload 外壳，直接对应规划书第 18 章的数据质量要求）：

```json
{
  "device_code": "living_room_light_01",
  "observed_at": "2026-10-14T19:30:00+08:00",
  "seq": 1024,
  "source": "simulator",
  "quality": "good",
  "metrics": { "power_on": true, "brightness": 60 },
  "units": { "brightness": "%" }
}
```

- `observed_at`：**观测时间**，不是入库时间；
- `seq`：单调递增序号，用于丢包/乱序/重复检测（规划书风险清单里的"MQTT 消息乱序/重复"靠它兜）；
- `quality` / `is_stale`：质量码与过期标记，**过期数据不得伪装实时值**。

### 2.4 Agent 编排：LangGraph（但必须按 v1 规范写）

⚠️ **这是本次选型最重要的一条技术修订**，直接推翻规划书第 13.5 节的代码骨架：

| 规划书写法（已过时） | LangGraph v1 正确写法 |
|---|---|
| `from langgraph.prebuilt import create_react_agent` | `from langchain.agents import create_agent` |
| `create_react_agent(model, tools, prompt=...)` | `create_agent(model, tools, system_prompt=...)` |
| `HumanInterruptConfig` / `HumanInterrupt` | `langchain.agents.middleware.human_in_the_loop` 下的 `InterruptOnConfig` |
| `langchain_community.embeddings.dashscope` | `langchain_openai.OpenAIEmbeddings` + compatible-mode base_url |
| `langchain_community.vectorstores.Chroma` | `langchain_chroma.Chroma` |
| 同步校验节点 `ValidationNode` | `create_agent` 自动校验工具入参 |

- **依据**：LangGraph v1 迁移指南明确"**弃用 `create_react_agent`，改用 LangChain 的 `create_agent`**"，两者 import 路径、prompt 参数名（`prompt`→`system_prompt`）、钩子机制（pre/post-model hook → middleware）全部变化；`HumanInterrupt*` 系列也整体迁入 middleware。
- **对本项目的实际收益**：规划书最核心的安全设计——"高风险操作只生成待确认建议"——在 v1 里**正好由 human-in-the-loop 中间件承载**（`interrupt` 暂停 → 前端二次确认 → 恢复执行）。这比自己手写暂停节点更省事，也和"确认矩阵"（规划书第 16 章）天然对应。
- **落地纪律**：
  1. **一次性装齐并锁版本**，安装后立刻跑 import 冒烟测试（见 §6.1）；
  2. `langgraph-checkpoint-mysql` 提供 MySQL checkpointer → 会话状态与中断现场落 MySQL，**不再引入 Redis**；
  3. Agent 侧只保留白名单工具，**代码里不存在"直接执行门锁/燃气"的通道**（规划书第 9 章第 5 条），这一点不因框架更换而放松。

### 2.5 Agent 骨架：手写 `StateGraph` 编排，节点内部用 `create_agent`（v1.1 细化）

资料里存在**两条都学过、且都正确**的路径，必须说清各自用在哪：

| 路径 | 出处 | 用在哪 |
|---|---|---|
| **A. 手写 `StateGraph` + `interrupt()` / `Command(resume)`** | `资料/02_LangGraph进阶_Human-in-the-loop.md`（完整代码 + 状态快照演示） | **本项目主线**：多 Agent 显式路由 + 高风险暂停节点 |
| **B. `create_agent` + `langchain.agents.middleware`** | `资料/policy-db-agent-plan.md` §8.6、`资料/02_LangChain 核心组件.md` | **节点内部**：每个专业 Agent 自己的思考-工具循环与安全中间件 |

**为什么主线选 A 而不是 B**：
1. 本项目要的是**确定性路由 + 可审计**，而不是"让模型自己决定调哪个工具"。规划书要求"任务被判定属于哪一个（或哪几个）家居智能体的业务范围"，这个判断必须是**图上的边**，不能藏在模型的隐式决策里；
2. 高风险动作的暂停点必须**在图上看得见**——`资料/7大架构速览.md` 对 7 号 Graph/Workflow 的评价就是"金融/医疗这类每一步都要可审计、出问题能回溯的生产系统"，本项目的高风险设备正好属于这一类；
3. 你在这条路上已经有可运行的完整代码（含 `MemorySaver` → `SqliteSaver` 的持久化演进），**换到中间件路径等于把已掌握的东西丢掉**。

**推荐骨架**（协调 Agent 用 Router 思路，专业 Agent 作为节点或子图）：

```text
START
  └─▶ [协调/路由节点]        # 判意图、识别发言人、拆任务（可用结构化输出）
        ├─▶ [编排控制 Agent] ─┐
        ├─▶ [安防应急 Agent] ─┤
        ├─▶ [能源优化 Agent] ─┼─▶ [高风险确认节点]？── interrupt() ──▶ 人工确认
        ├─▶ [健康照护 Agent] ─┤         │                              │
        └─▶ [家务助理 Agent] ─┘         │◀──── Command(resume) ────────┘
                                        ▼
                                   [汇总/输出节点] ─▶ END
```

- 每个方括号节点**内部**用 `create_agent(model, tools, system_prompt=..., middleware=[...])`，工具即为规划书第 13 章的白名单工具；
- 中间件按既有规划先上两个性价比最高的：`ModelCallLimitMiddleware(max_calls=8)`、`ToolCallLimitMiddleware(tool_name="propose_action", max_calls=4)`；
- `HumanInTheLoopMiddleware`（`资料/05_DeepAgents.md` 提到，配合 `interrupt_on` 配置）作为**备选省事方案**：若某些 Agent 内部需要暂停，直接开中间件比手写节点快。

**Checkpoint 落库（实测确认的用法）**：

```python
from langgraph.checkpoint.mysql.pymysql import PyMySQLSaver    # 同步版，配 PyMySQL

with PyMySQLSaver.from_conn_string(CHECKPOINT_DB_URI) as cp:
    cp.setup()                       # 首次必须调用，否则表不存在
    graph = builder.compile(checkpointer=cp)
```

| 要点 | 说明 |
|---|---|
| 类名 | 同步是 **`PyMySQLSaver`**，异步是 **`AIOMySQLSaver`**（`langgraph.checkpoint.mysql.aio`）——**不是 `MySQLSaver`** |
| 安装 | 同步需额外装 `langgraph-checkpoint-mysql[pymysql]` |
| 首次运行 | 必须调 `.setup()` 建表；手工传连接时必须 `autocommit=True`，否则建表不提交 |
| **独立库** | **不要塞进业务库 `smart_home`**——`资料/policy-db-agent-plan.md` §8.5 明确提醒过：表结构由框架管理，混进业务库会污染 `include_tables` 白名单。单独建 `smart_home_checkpoint` 库 |

**为什么把 asyncmy 换成 PyMySQL（这是 v1.1 的一处主动降级）**：

| 维度 | asyncmy（v1.0 方案） | **PyMySQL 同步（v1.1 采纳）** |
|---|---|---|
| 与既有资产一致 | ✗ 你没用过 | ✓ `policy-db-agent-plan` §8.1 与个人 RAG 项目都是同步引擎 |
| 家庭场景并发（5~8 人） | 过剩 | 足够 |
| 踩坑面 | 事件循环里混同步调用会卡死，要时刻警惕 | LangGraph 的工具写成 `def`（同步）时，**框架自动丢线程池执行**，不需要你操心 |
| 代理/驱动兼容 | asyncmy 需编译，远程库握手异常更难排查 | 纯 Python，远程连接问题好定位 |
| 需要异步的层 | — | **保留在外层**：FastAPI 端点、LLM 调用、SSE 流式、MQTT 订阅仍全部 `async` |

> 一句话：**异步用在该用的地方（等网络、等模型），数据库这种"低并发 + 短事务"就老实同步**。真要转异步，把 `create_engine` 换 `create_async_engine`、驱动换 asyncmy 即可，接口不变——**这个决定是可逆的**。

**远程实例（虚拟机）相比本机库要多操心的 4 件事**：

1. **网络可达**：确认虚拟机用桥接/NAT 端口转发，本机能 `ping` 通且 **3306 可达**；虚拟机 `my.cnf` 的 `bind-address` 不能是 `127.0.0.1`（否则只监听回环）；
2. **专项账号 + 来源限制**：不要用 `root` 远程登录。建 `agent_ro@'%'`（或限定本机 IP）并只给 `SELECT`，业务写操作另开 `app_rw` 账号；这正好落实规划书的"护栏第 1 层"；
3. **超时与重连**：`connect_args={"connect_timeout": 10}` + `pool_pre_ping=True` + `pool_recycle=3600`，虚拟机会挂起/休眠时尤其重要；
4. **字符集一致性**：库、表、连接三处都要 `utf8mb4`，否则中文设备名会变问号——远程连接最容易在这里翻车。

**其他**：
- MySQL 版本建议 **8.0 而非 8.4 LTS**：规划书按 8.0 写，8.0 的资料/踩坑记录最多。
- 时序数据（`device_readings` / `energy_readings`）**首期不做分区与降采样**，但必须：① 查询接口强制最大时间窗；② 返回行数上限；③ 写入端限频。规划书风险清单里"时序查询过重拖垮库"靠这三条挡。

## 5. 「没有真实数据采集」的影响与对策（重点章）

这是本项目最需要提前处理的结构性约束。**它不是一个"缺陷"，而是一个必须被设计进架构的前提。**

### 5.1 影响面逐条拆解

| 受影响项 | 具体影响 | 危险后果 |
|---|---|---|
| 数据来源 | 全部数据来自模拟器 / MQTTX / CSV | 数据是"编"的，容易被质疑结论无意义 |
| 数据真实性 | 无真实设备时序、无真实电价账单、无真实成员作息 | 能耗省费数字、照护异常阈值都**没有基准** |
| 时序特征 | 模拟数据可能过于"完美"（无抖动、无缺失、无跳变） | 演示很漂亮，但经不起追问"真实数据长这样吗" |
| 设备能力 | 能力档案是自己写的 | 容易写出真实设备根本不支持的能力 |
| 展示可信度 | 界面上的"实测值"其实是模拟值 | **如果不标注，等于对用户说谎**——这违反规划书第 17 章"禁止虚构实时性" |
| 验收 | 规划书 §14/§20 的量化指标需要"已确认基准集" | 没有真数据，指标只能对模拟数据集定义 |

### 5.2 三条对策

**对策一：数据源做成可插拔（`DataSource` 抽象 + `DATA_MODE` 开关）**

```text
DATA_MODE=mock        # 内置生成器直接产生并写库（不启 MQTT，最省事）
DATA_MODE=mqtt        # 订阅 MQTT（数据生成器 / MQTTX 手工注入）  ← 本次选定
DATA_MODE=csv         # 受控 CSV 导入（做验收基准集用）
DATA_MODE=real_gateway# 将来接 Home Assistant / Matter
```

关键：**上层代码（Agent、API、前端）对数据来源完全无感**，只认统一信封里的 `observed_at/source/quality`。这样"没有真实采集"就变成"换了个适配器"，而不是"系统缺了一块"。

**对策二：生成器必须有"物理合理性"，不能是随机数**

这是模拟数据可信度的分水岭。数据生成器（`gateway/simulator/`）要做到：

- **温度有惯性**：空调设定 26℃，室温不是瞬间跳到 26℃，而是按一阶惯性逼近，且有 ±0.3℃ 抖动；
- **功率曲线有形状**：空调启停有尖峰、待机有底噪、照明有日落同步；
- **电价有时段**：峰/平/谷三段，与用能曲线叠加后能算出"如果挪到谷段能省多少"；
- **活动节律有人味**：老人起夜、儿童放学、工作日/周末不同；
- **支持时间倍速**：`--speed 60` 让 24 小时数据 24 秒跑完 —— 能耗看板和照护时间轴才演示得动。

**并且刻意注入"坏数据"**：缺失、跳变、越界、重复 `seq`、时间倒流。**因为这些正是要被系统识别出来的东西**，没有它们，数据质量治理那一套就无从验证（也拿不到规划书 §20 里"数据质量识别率 ≥95%"这个分）。

**对策三：全链路元数据 + 全界面标注**

- 每条数据必带 `observed_at` / `source` / `quality` / `is_stale`；
- **界面上所有模拟数据必须显式标注来源**（如角标"模拟数据"或详情里 `source: simulator`），规划书 §11.3 上线清单已要求"虚拟设备与真实设备在界面中明确区分"；
- 报告里保存"输入时间窗 + 数据版本 + 计算口径 + 生成时间"，让人能复盘。

### 5.3 三条红线不因"没有真数据"而放松

| 红线 | 保持方式 |
|---|---|
| 门锁/燃气/总闸/布防撤防**只生成待确认项** | 工具层不存在执行通道 + HITL 中间件暂停 + 后端强制置 `pending_confirm` |
| 数据不足时**不给确定性省费金额** | 能耗建议必须回带输入曲线与计算口径，缺数据就标注"待确认"而非估算 |
| 健康异常**只能表述为"待确认线索"** | system prompt 硬约束 + 输出分区（观测事实 vs 可能原因分开显示） |

**这三条恰恰是"没有真实数据"时最容易被自己放松的地方**——因为演示时想给出漂亮结论。要提前定死。

### 5.4 对答辩/汇报表述的建议

不要把"没有真实采集"当短板解释，把它讲成设计决定：

1. **平台与数据解耦**：数据源可插拔（mock / mqtt / csv / real_gateway），接真机是"换适配器"而非"改架构"；
2. **数据质量可治理**：从消息信封的 `observed_at/source/quality/seq`，到导入校验、过期标注、界面区分，是一条完整的质量链路；
3. **安全边界是主动选择**：不自动执行高风险设备，不是因为做不到，而是因为**家庭场景下"误开门锁"的代价不可承受**；
4. **诚实优先**：模拟数据全程标注，模型不可用时明确降级提示。

> 这套说法比"我们有 32 台虚拟设备在跳动"要硬得多——**它展示的是工程判断力，而不是数据量。**

**建表时的几个设计决定（值得写进答辩）**：

1. **每个表、每个字段都写了 COMMENT**：不是为好看，而是字段 COMMENT 会被 LangChain 的 `get_table_info()` 拼进提示词，是提升模型"看懂表结构"性价比最高的一招。
2. **向量不存 MySQL**：`knowledge_chunks` / `memories` 只存原文与可追溯元数据，用 `chroma_id` 关联 Chroma。避免同一份向量存两处，也不会把 MySQL 撑肿。
3. **遥测按"指标"存（EAV）而不是宽表**：`device_readings` 一行一个 metric，才能容纳"一条消息里既有温度又有湿度"的统一信封，且加新指标不用改表。
4. **`device_capabilities` 是防臆造的核心表**：带 `value_min/value_max/enum_values/risk_level`，模型必须先查它才能下发控制指令。
5. **高风险在数据层就标记**：`devices.high_risk` 与 `device_commands.status`（`pending_confirm` 为默认值）双重保障——**指令默认就是"待确认"，而不是默认执行**。
6. **审计与记忆带来源**：`memories` 有 `source/confidence/decay_at`，`audit_events` 记 action/object/改前改后，满足"可解释、可追溯、可删除"。

### 12.10 设备清单评审与修订（v1.8 新增）

**评审起因**：M0 完成后对 30 台设备逐台过了一遍，判断哪些删、哪些留。

**本次实际变更：新增 2 台卧室温湿度传感器**

| 新增设备 | 编码 | 房间 |
|---|---|---|
| 主卧温湿度传感器 | `master_bedroom_temp_sensor` | 主卧 |

**为什么要加**：原设计**只有客厅装了温湿度传感器**，这会导致一个尴尬后果——做"睡眠模式"要调卧室温度时，**系统根本读不到卧室温度，只能回"无数据"**。而卧室恰恰是睡眠场景的主角，这个缺口在演示时会被一眼看出来。

**改动方式**：数据库 + `04_seed.sql` **两处同步**（否则脚本重跑会把新增的两台冲掉）。能力档案复用现有 `temp_sensor` 模板自动展开，无需手写。

**变更后核对**：

| 项 | 变更前 | 变更后 | 校验 |
|---|---|---|---|
| 设备总数 | 30 | **32** | ✓ |
| 设备能力 | 55 | **59** | ✓ **+4 = 2 台 × 每台 2 个能力**，加减对得上，说明"新增设备自动获得能力"链路是通的 |
| 传感器台数 | 8 | **10** | ✓ |
| 温湿度覆盖房间 | 客厅 | 客厅 / 主卧 / 次卧 | ✓ 三个需要控温的房间全覆盖 |
| 高风险设备 | 3 | 3（未变） | ✓ 门锁 / 燃气阀 / 总闸 |

**当前设备构成（32 台）**：玄关 3 / 客厅 8 / 厨房 5 / 卫生间 3 / 阳台 1 / 主卧 6 / 次卧 6。

**设备保留决策（已定）：8 项候选全部保留 —— 设备清单就此定稿为 32 台**

评审中曾把下列 8 台标记为"装饰性或功能重复"：

| 编码 | 设备 | 当时的标记 |
|---|---|---|
| `entryway_light` | 玄关灯 | 为凑房间，无演示价值 |
| `kitchen_light` | 厨房灯 | 厨房戏份在燃气/水浸/烟感，灯是陪衬 |
| `bathroom_light` | 卫生间灯 | 装饰性 |
| `bathroom_water_leak_sensor` | 卫生间水浸传感器 | 与厨房水浸完全重复 |
| `balcony_light` | 阳台灯 | 装饰性 |
| `master_bedroom_light_bedside` | 主卧床头灯 | 与主卧主灯重复 |
| `master_bedroom_humidifier` | 主卧加湿器 | 只在睡眠模式露一次脸 |
| `second_bedroom_curtain` | 次卧窗帘 | 窗帘已有客厅 + 主卧两处 |

**用户决定：全部保留。理由 —— "保留这些功能更能体现这是一个房间"。**

> **这条决策修正了评审的方向，值得记下来**：设备数的"精简"不是目标，**空间的完整性**才是。
> 一盏灯在功能上确实可被忽略，但它决定了"这个房间像不像一个真实的房间"。
> 演示类项目里，**住宅的可信度**比设备清单的紧凑度更重要 ——
> 若只按"有没有独立演示价值"来砍，会把一套住宅砍成一个功能点集合。
> 这个判断标准对后续"要不要加设备"同样适用：**从完整房间出发，而不是从功能清单出发**。

**评估时发现的另外两个缺口**（方向与上一条一致，属"要不要补"，待用户决定）：

1. **没有冰箱**（厨房）—— `家务助理 Agent` 的"库存识别、补货建议"与能耗侧的"待机功耗"都指望它，目前这块是空的；
2. **没有洗衣机**（阳台或卫生间）—— 能耗演示的大功率负载偏少（现只有空调 + 热水器）。

**一条值得记住的评审原则**：判断一台设备该不该留，不要问"真实家庭有没有这个东西"，而要问 **"哪个演示场景会用到它"**。同一个问题的另一面是——**留着的每台设备都要有明确用途，否则它只是在给生成器和工具层增加无谓的维护面**。

### 12.12 M1 第二块：数据生成器（v1.10 新增）

**交付文件**（`gateway/simulator/`，独立进程，不 import backend）

| 文件 | 作用 |
|---|---|
| `device_profiles.yaml` | 物理与行为档案：环境温度曲线、分时电价、房间热工参数、各房间占用时段、各设备类型功耗与开关时段 |
| `registry.py` | 从数据库读设备清单与能力档案（自己读 `.env` + pymysql，保持独立进程） |
| `physics.py` | 物理引擎：温度惯性、湿度、水箱、功率、活动量 |
| `faults.py` | 坏数据注入（6 类） |
| `scenarios.py` | 6 个预置场景 |
| `publisher.py` | 主循环 + CLI（时间倍速 / dry-run / 进度统计） |

**一个重要的分工决定**：**设备清单从数据库读，物理参数放 YAML**。
这样"加/删设备"只改数据库，"调真实感"只改 YAML，两边不会互相牵连。
额外好处：生成器能拿到能力档案声明的取值范围，**产出的数据天然不会超出设备能力**（不会出现"亮度 150%"这种自相矛盾的值）。

**"像真的"三个要点**

1. **温度有惯性**：一阶惯性模型（`T = T目标 + (T - T目标)·e^(-Δt/τ)`），关空调时缓慢漂向自然室温。
2. **功率与物理状态耦合**：空调功率不是随便给的，而是由"温度是否超标 + 恒温器死区"决定。**这是能耗曲线可不可信的关键。**
3. **人的活动有节律**：占用状态按房间/时段抽样，且**同一小时内结果稳定**（否则灯会一秒一闪）。

**迭代中修掉的 4 个问题（这部分最值得看）**

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 启动直接 `KeyError: indoor_bias` | 参数放错层级（在 `environment` 下，却从 `indoor` 取） | 改取值路径 |
| 2 | **空调"把房间加热到 27℃"** | 我把空调当成双向温控。实际**空调只能制冷** —— 自然室温 24℃、设定值 27℃ 时，它根本不该启动 | 增加 `natural_indoor()` / `ac_cooling_demand()`：只有自然室温高于设定值才有制冷需求 |
| 3 | **压缩机"制冷一次就再也不动"** | 温度被精确停在设定值上，没有回差，永远不需要再次启动 | 引入**恒温器死区**（超过设定值 0.3℃ 才启动、降到设定值就停） |
| 4 | 压缩机连续运转，看不到启停 | **制冷速率比房间吸热速率还慢**，温度卡在死区上方降不下来 | 把制冷时间常数显式设为 `ac_cooling_tau_min: 5.0`（远快于吸热） |
| 5 | 32 台设备只产出 31 个 topic | `gas_valve` 在指标函数里漏了处理，被静默跳过 | 补上分支（只上报阀门状态，**永不主动关闭它**） |

**交付文件**

| `backend/tests/ingest_check.py` | 三层验证脚本 |

**落库映射**

| 消息 kind | 去向 |
|---|---|
| `state` / `telemetry` | `device_readings`（EAV：一个 metric 一行） |
| 含 `power_w` 的消息 | 额外落 `energy_readings`（功率 + 增量电量 + 峰平谷标签） |
| `event` | `sensor_events`（原样存档 payload，可追溯） |
| `cmd` / `cmd_ack` | **不落库** —— 那是"后端 → 设备"方向，不属于观测数据 |

**值编码规则**：数值（含 bool）→ `value_num`；字符串 / 枚举 → `value_text`。
于是"空调开机时长"是 `AVG(value_num)`，"当前模式"是 `value_text = 'cool'`。

**六个设计决定**

1. **批量落库 + 线程池**：SQLAlchemy 是同步的，写远程库一次往返不便宜。
   先缓冲、按批 `executemany` 提交，并且统一丢 `asyncio.to_thread()` ——
   直接在事件循环里写库会阻塞整个后端（表现为"LLM 流式输出莫名卡顿"）。
2. **最新值缓存只收 `quality=good` 且非 stale 的值**：坏数据仍入库留痕，
   但绝不进缓存 —— "最新值"一旦被污染，后面所有判断都建立在脏值上。
3. **`observed_at` 统一存本地时区 naive 时间**：分时电价与作息节律都按本地时间定义，
   存本地时间就不必在每个查询处做时区换算（那是最容易出错的地方）。跨时区部署时改 `settings.timezone` 一处。
4. **未知设备拒收**：不在 `devices` 表里的 code 不写库（避免外键报错，更避免凭空造出数据）。
5. **坏数据入库但打标，不丢弃**：不入库就没法做质量复盘，也不符合审计留痕要求；
   污染问题靠标记 + 下游 `WHERE quality='good' AND is_stale=0` 过滤解决。
6. **电价独立成共享配置 `config/tariff.yaml`**：它同时被落库（打标签）与能耗分析（算省费）消费，
   两处各写一份必然漂移。

**三个坑（这部分最值得看）**

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 订阅服务始终连不上 broker，报错堆栈落在 `paho/.../__del__`，**看起来像可以忽略的垃圾回收噪声** | aiomqtt 底层是 paho 的 asyncio 封装，用 `loop.add_writer()` 驱动 socket；**Windows 默认的 ProactorEventLoop 在 `add_writer/remove_writer` 上直接抛 `NotImplementedError`** | 切 `WindowsSelectorEventLoopPolicy`；⚠️ **必须在事件循环创建前设置**，且 **M2 的 FastAPI 也要**（uvicorn 在 Windows 同样默认 Proactor，否则订阅任务会"接口正常、数据不进库"） |
| 2 | 一轮 1233 条数据里 **510 条被误标 `is_stale`**，最新值缓存从 32 台掉到 30 台 | broker 在订阅瞬间回放 **22 条 retained 快照**（`state` 是 retained 的），其时间戳是**上一轮模拟到的"未来时刻"**（16:04）。它被当成"上一条"的时间基准，于是接下来所有实时数据都被判成"时间倒退" | retained 消息**照常入库但单独计数、不参与时间基准判定**（216 行 → 误标归零）。`22 台 × 24 拍 ≈ 528` 与观察值吻合，定位闭环 |
| 3 | 生成器多轮运行时，新一轮数据整体"时间倒退" | 每轮默认都从"当前时刻"重新开始，而库里/broker 上已有**更晚时间戳**的数据 | 生成器 `--start` 默认改为 `auto`：**取 max(库里最新数据, 当前时刻)**，从它之后续跑。实测续跑起点正确打印为"库里已有至 10-15 16:04:10 的数据" |

> **坑 #2 与坑 #3 是同一个问题的两端**：一端是"消费方不该拿历史快照当时间基准"，
> 另一端是"生产方不该让时间轴回退"。两处都修了，所以它们是双重保险。
> 这类"数据源时间轴"的问题在真实 IoT 项目里很常见（设备时钟漂移、网关补发、重放历史），
> 答辩时讲这一条比讲"我们用了 MQTT"有分量得多。

**已实现端点（严格对齐规划书 §10.3 契约）**

```text

GET /api/energy/summary                  ✅ 能耗汇总（分时电价 + 高耗设备 + 逐小时）
```

**四个关键技术决定**

1. **订阅服务跑在独立线程，不内嵌 FastAPI 的事件循环**（见 §12.13 坑 #1 的后续）。
   aiomqtt 要 SelectorEventLoop，而 uvicorn 在 Windows 上用 Proactor（`--reload` 时更显式设置），
   而"事件循环创建后不能改类型"——内嵌无干净解法。
   独立线程自带循环，与 uvicorn 用什么循环**完全无关**（`--reload` 也能用），
   而且仍在同进程内**共享缓存**。代价：缓存要加锁（已加 `RLock`）。
2. **需要查库的端点写成 `def` 而不是 `async def`**。
   同步 SQLAlchemy 直接跑在事件循环里会卡住整个后端（症状：一个人查历史数据，所有人跟着卡）。
   写成 `def`，FastAPI 自动丢线程池执行 —— **这条约定适用于本项目所有查库端点**。
3. **两个缓存实例的坑（本项目最隐蔽的一个 bug）**。
   `Ingestor.__init__` 里自己 `new` 了一个 `LatestValueCache`，而 API 的 `app.state.cache` 是另一个实例
   → **一个在写、一个在读**。症状极具迷惑性：health 显示"MQTT 已连接、收到 1032 条、数据在正常入库"，
   但接口读到的**永远是启动时的预热值**、32 台设备全部显示"离线"——两边单看都"在工作"，只是根本没接上。
   修法：缓存改为可注入，`main.py` 把 `app.state.cache` 传进 ingestor。
4. **缺省时间窗以"数据最新时间"为锚点，而不是"现在"**。
   模拟器按倍速跑，数据时间会跑到真实时钟之外（本次跑到了次日）。
   此时"现在往前 24 小时"**一条都查不到** —— 用户看到"没有数据"，而数据好好躺在库里。
   锚点在 health 里暴露为 `data_anchor`；真实部署时 `anchor ≈ now`，行为与旧写法完全等价。

**三个时间语义（极易混淆，已写进代码注释）**

| 概念 | 含义 | 用途 |
|---|---|---|
| `observed_at` | 设备/网关报出的**观测时间**。可能不准、可能在未来、可能是补发 | 展示"这个值什么时候测的" |
| `received_at` | 我们**实际收到消息的本机时间** | **判断设备是否在线** |
| `last_observed_at` | 手上最新数据的观测时间（**含启动预热**） | 展示"数据更新时间" |

**两个被修正的语义错误（都是实测踩出来的）**

| # | 错误做法 | 后果 | 修法 |
|---|---|---|---|
| 1 | 预热时也更新"在线时间" | 库里数据时间戳很新 → **MQTT 完全没连上，32 台设备却全部显示"在线"** | 预热只填值，**不碰** `_last_seen_live` |
| 2 | 用 `observed_at` 判断在线 | 设备时钟跑到未来 → "永远在线" | 改用 `received_at`（本机接收时间） |
| 3 | broker 回放的 retained 计入在线 | "broker 上存着它的最后状态"被当成"它现在在发数据" | retained 入库但 `count_as_live=False` |

**实测结果（broker + 生成器 + API 三者同时运行）**

```text

实时值     : seq=35、last_seen=2026-10-15T14:58:01（本机接收时间）
```

**三个技术决定**

1. **语料用 Markdown，不用 PDF** —— 环境里只有 `pypdf`（能读不能写），没有 PDF 生成库；
   而 Markdown 人可读、可改、diff 友好。**但 loader 同时支持 `md` / `txt` / `pdf`**：
   将来拿到真实的厂商说明书 PDF，直接丢进 `data/raw/` 再跑一次灌库即可，代码一行不用改。
   （真要生成 PDF 再加 `fpdf2` 之类也不迟，现在没必要为格式多一个依赖。）
2. **按章节切分，而不是整篇直接切** —— 每块都带"来自哪份文档的哪一节"，
   引用才能精确到节（规划书要求"记忆依据"可追溯）；而且「空调温度与耗电的关系」这一节
   不会被切碎后混进别的主题。章节内部再由 `RecursiveCharacterTextSplitter` 做二级切分
   （`chunk_size=800, overlap=100`，与规划书 §13.2 一致）。
3. **首期不启用 rerank** —— 69 块的语料规模下向量召回已经足够；
   rerank 走不了 OpenAI 兼容协议（要用 DashScope 原生 SDK），多一层依赖换来的收益不划算。
   等语料变大或出现"检索串味"再启用，`search()` 里已预留位置。

**两个 DashScope 兼容模式的坑（实测，已写进代码注释）**

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | `OpenAIEmbeddings` 默认 `check_embedding_ctx_length=True` | 它会把文本先转成 **token 数组**（OpenAI 专有协议），DashScope 不接受 → 直接报错 | 显式设 `check_embedding_ctx_length=False` |
| 2 | 单次请求文本条数超限 | embedding 接口返回 400 | 设 `chunk_size=10`（沿用既有 RAG 项目的取值） |

**一个刻意的边界：检索与生成分开**

如果混在一起，回答错了你根本不知道是"没找到资料"还是"找到了却编错了"。
回答与引用交给后续里程碑的 Agent，届时**引用必须带上 `source_file` + `section`**，

**核心设计一：冲突检测需要一个"可解释的判据"**

最典型的冲突是**跨设备**的：LLM 生成的"看电影模式"里同时有
「主灯亮度 100%」和「氛围灯 30%」—— 它们作用在不同设备上，
"同一设备同一能力被设了两次"这种检查**根本抓不到**。

解法是给场景一个**意图模板**（`config/scene_intents.yaml`）：为常见场景声明合理区间，
例如观影场景的 `brightness ≤ 40%`、`position ≤ 30%`（需要遮光）、`target_temp ∈ [24,27]`。
超出区间的动作被剔除，**原因写清楚判据**：

```text
被剔除的动作及原因：
  · 客厅主灯 brightness=100
    ↳ 与「观影」场景冲突：观影场景需要环境偏暗，照明不宜超过 40%
  · 客厅窗帘 position=100
    ↳ 与「观影」场景冲突：观影场景需要遮光，窗帘开合度不宜超过 30%
最终动作序列：
  · 客厅氛围灯带 brightness=30
  · 客厅空调 target_temp=24 [clamped]（原值 20，按观影区间调整）
  · 客厅电视 power_on=True
  · 客厅智能音箱 power_on=True
```

放 YAML 而不是写死：判据会随家庭习惯变（有人观影时喜欢留一盏亮灯），
调判据不用改代码、不用重跑测试，也更容易向用户解释"为什么剔除了这一条"。

**核心设计二：编排的顺序不能换**

```text
能力校验 → 重复检测 → 意图约束 → 风险标记
```

- **先校验再判重**：否则会拿"根本不存在的设备"去互相比较；
- **判重放在意图约束之前**：先确定"最终想设成什么值"，再看它是否符合场景意图。
  反过来会出现"两个值都被意图拒绝、但其实其中一个 clamp 之后合法"这种绕圈情况；
- **风险标记放最后，而且不剔除**：剔除会让用户误以为"系统不支持门锁"，
  事实是"支持，但需要你确认"——这两种说法对用户的意义完全不同。

**核心设计三：执行的三条归宿 + 一条不可降级的红线**

| 情况 | 处理 | 落库状态 |
|---|---|---|
| 高风险设备（门锁/燃气阀/总闸） | 只生成待确认建议，**绝不执行** | `pending_confirm` |
| 普通设备 | 发 MQTT 指令 | `executed` |
| 发送失败（重试 3 次仍失败） | 记录失败，**继续执行其余动作** | `failed` |

单步失败**不中断整场**（看电影模式里"音箱没连上"不该导致"灯也不开了"），
整体状态标 `partial` 并置 `fallback_used=true` —— 这是"失败重试降级"的落点。

> ⚠️ **不可降级的是高风险**：网络再差、重试再多次，门锁也不会因此被"顺手打开"。
> 而且这不靠调用方自觉：`executor.create_command()` 里有一行强制代码 ——
> 任何试图给高风险设备写 `executed` 的调用都会被掰回 `pending_confirm`，
> 数据库那一层还有默认值作为第二道保险。**红线要写在代码里，不能只写在文档里。**

**核心设计四：让"执行"真的有效果（生成器响应指令）**

原先生成器只发不收，"执行场景"会变成空壳：后端写了记录、发了 MQTT，设备状态纹丝不动，
演示时看起来就像"点了没反应"。所以给生成器加了订阅与响应：

```text
后端下发 cmd → 模拟器应用覆盖（apply_command）
             → 后续 state 上报反映新状态
             → 订阅端落库/进缓存
             → API 查询立刻能看到变化
```

两个设计细节：
1. **覆盖带 TTL（60 模拟分钟）**：真实设备被手动控制后，过一段时间自动策略仍会接管；
   若覆盖永不过期，跑一晚上就变成"灯永远关着"，与作息模型彻底脱节。
2. **设备侧要再校验一遍**：就算后端已校验过，设备自己也要验（真实设备就是这样，
   它不会因为"上游说合法"就照做）；校验不通过要**回 ack 说明失败** ——
   让后端一直以为"发成功了"是比"下发失败"更糟的状态。

**闭环实测（broker + 生成器 + API 三者同跑）**

```text
① 执行前   客厅主灯 = {brightness: 68, power_on: False}
② 执行场景 status=success  executed=3  pending=0  failed=0
             ✅ 客厅主灯 power_on=True   (command_id=1)
             ✅ 客厅主灯 brightness=15   (command_id=2)
             ✅ 客厅氛围灯带 brightness=25 (command_id=3)
③ 生成器侧 (日志原文)
             ✅ 收到指令 living_room_light_main.brightness=15 → 已应用（60 模拟分钟后恢复自动推演）
④ 执行后   客厅主灯 = {brightness: 15, power_on: True}
⑤ 入库确认 最近 6 条 brightness = [92, 50, 51, 68, 15, 15]   ← 15 即指令值
⑥ API 复查 氛围灯带 30 / 空调 24 / 电视 on / 音箱 on  —— 全部与指令一致
```

#### 12.17.2 拓扑：为什么"扇出"是图上的边，不是模型的行为

```
START → route ──(按路由结论 Send 扇出)──┬→ scene_node     ─┐
                                        ├→ security_node  ─┤
                                        ├→ energy_node    ─┼→ aggregate → plan
                                        ├→ care_node      ─┤              ↓
                                        └→ assistant_node ─┘         execute_low
                                      （无助手时直接进 aggregate）          ↓
                                                                    confirm（interrupt）
                                                                           ↓
                                                                    execute_high → respond → END
```

条件边 `_fan_out` 只是**照着 `route.agents` 扇出**，不做二次判断。这样"这次跑了哪几个助手"
是图上可见的事实（可审计、可单测），加第 6 个助手只需动 `ALL_AGENTS` 一处。

#### 12.17.3 三个关键设计决定

1. **执行拆成两段，而不是"全部挂起、恢复后一起执行"**
   低风险 → `execute_low` 立刻跑 → 高风险才 `interrupt` → 恢复后 `execute_high`。
   差别在于用户迟迟不确认时，**低风险动作已经生效了** —— 这才符合
   "其他直接执行，执行完告知"（用户 2026-10-15 确认的要求）。

2. **待确认指令在 `interrupt()` 之前就落库，且必须幂等**
   早先版本是"批准后再写库"，结果中断期间数据库里没有任何痕迹，
   待确认列表只能靠进程内存维护（进程一重启弹窗就消失）。
   现在 `confirm_gate` 先写一条 `pending_confirm` 并把 `command_id` 回填到待确认项，
   批准后是**更新那一行**（补 `confirmed_at` 与说明），不是再插一条。
   ⚠️ 幂等是**必须的**：`Command(resume=...)` 会**重新执行**被中断的节点
   （这次 `interrupt()` 直接返回恢复值），不幂等就会批准一次多一条待办。

3. **汇总与回答节点刻意不调模型**
   模型负责"想做什么"，代码负责"能不能做、做了会怎样"。
   结构化之后汇总退化成字段拼接：可测、可复现，且事实与建议天然分开
   （正好满足规划书 §10.2 的回答分区要求）。让模型"再总结一遍"是信息二次损耗 + 多一次幻觉机会。

#### 12.17.4 修掉的三个"服务起不来 / 看起来像别的问题"的 bug

| 现象 | 根因 |
|---|---|
| `run_api.py` 报 `TypeError: 'property' object is not callable` | `effective_api_host` 被**重复套了两层 `@property`** |

#### 12.17.5 序列化白名单（定时炸弹，不是可忽略的噪声）

图状态里放的是 Pydantic 模型，不登记白名单时 LangGraph 每次反序列化都会警告

### 12.18 M5 第一块：Web 大屏（PC 浏览器）—— **完成**（v1.17 新增）

#### 12.18.1 与大屏并列的手机端是**两个独立工程**

用户要求"大屏与手机端独立"，所以：

#### 12.18.4 四条不能破的规矩（写进代码里，不是写在文档里）

1. **接口字段只有一处定义** —— 全在 `src/api/`。页面不直接拼 URL、不猜字段，
   后端改 schema 时改动集中在一个文件。
2. **空值显示 `—`，绝不用 0 冒充** —— `utils/format.js` 里所有格式化函数在收到

3. **模拟数据必须显式标注** —— 顶栏"数据时间"旁有 `模拟` 角标

4. **高风险永不自动执行** —— 侧栏底部常驻红线；每次确认弹窗都写明

1. **`health.devices` 的键是 `total`，不是 `devices`**（真 bug，已修）。

   最终靠"契约对账脚本对真实响应断言字段名"抓出来。
2. **npm 默认源只有 13 KB/s**：装了 11 分钟连 `node_modules` 都没建出来。

3. **npm 11 默认拦截安装脚本**（报 esbuild / vue-demi 未执行）。
   实测 esbuild 的 Windows 二进制随平台包 `@esbuild/win32-x64` 一起提供，
   **不需要 postinstall 下载**，`require('esbuild')` 正常 → 不影响，无需处理。

### 12.19 真实模型链路打通 + 路由空转漏洞修复 —— **完成**（v1.18 新增）

#### 12.19.1 三个把"模型不可用"伪装成"额度耗尽"的坑

前几版一直认为"模型免费额度耗尽、代码没问题"。换用**未被自己打过的干净模型**
做「单次 / 连发 10 / 并发 5」对照后，真正原因才浮出来：

**坑 1 — 动态别名不走免费额度。** 同一 key、同一时刻、同一请求体，只换模型名：

| 模型名 | 结果 |
|---|---|
| `qwen-plus` / `qwen-plus-latest` / `qwen-flash` | ❌ `403 AllocationQuota.FreeTierOnly` |
| `qwen-plus-2025-01-25 / -04-28 / -07-14 / -11-05 / -12-01` | ✅ 200 |

免费额度按**具体模型版本**发放，`-latest` 之类别名不做映射。
→ 落脚：模型名必须写全版本号。

**坑 2 — 真正的主因是 QPM 限流，不是额度问题。**

| 模型 | 单次 | 连发 10 次（无间隔） | 并发 5 次 |
|---|---|---|---|
| `qwen3.7-plus` | ✅ | **10/10** | **5/5** |
| `qwen-plus-2025-11-05` | ✅ | **7/10**（3 次拒） | **4/5**（1 次拒） |

失败码 `429 limit_requests`。多 Agent 一次对话要连发 5~10 个请求
（router + Agent 工具循环 + respond），正好撞上 plus 版本的每分钟请求数配额；
而 `qwen3.7-plus` 同样密集调用一次不拒。
→ 这解释了"单条调用没问题、跑多 Agent 就报错"的现象，但**与 key 能力无关**。

**坑 3 — 思考型模型与结构化输出冲突。**

```
400 The tool_choice parameter does not support being set to required or object
    in thinking mode
```

`qwen3.x` 在思考模式下拒绝 **object 形式**的 `tool_choice`，而 LangChain 的
`response_format` / `with_structured_output` 恰恰用 object 形式（字符串 `"required"` 不受影响）。
→ 解决：`ChatOpenAI(extra_body={"enable_thinking": False})`，已做成配置项
`settings.llm_disable_thinking`（默认开，非思考模型传它无害）。

**最终配置**：`QWEN_MODEL_NAME=qwen3.7-plus`。

#### 12.19.2 路由空转漏洞（实测发现的真 bug）

**现象**：问"客厅现在多少度"只回一句"已处理完成"，没有任何数据。

**根因**：`ROUTER_PROMPT` 里写着"纯查状态不必激活任何助手，`agents` 留空数组"，
但**图上并没有"不激活助手也能回答"的通道** —— 只有助手持有工具，
路由为空就等于没人去查数据。

**两层修复**：

1. **提示词**：改为"查询类问题同样要激活助手"，并按查询对象给出映射
   （环境读数→`scene`、电费→`energy`、安全→`security`、老人→`care`、说明书→`assistant`）；
   只有寒暄与"系统能干什么"才留空。
2. **确定性兜底**：新增纯函数 `app/agent/router.py::apply_route_fallbacks()`，
   把三条边界规则集中起来（丢弃编造的 Agent 名 / 要反问时不激活 / **空路由兜底给场景助手**）。
   抽成纯函数是为了能直接单测 —— 提示词改了不代表模型一定听话，必须有代码兜底。

**修复后实测**（真实模型，4 类问题）：

| 提问 | 路由 | 结果 |
|---|---|---|
| 客厅现在多少度 | `scene` | 25.92℃ / 湿度 50.7%，并**主动标注数据已过期** |
| 燃气报警器多久检查一次 | `assistant` | 说明书：3 个月除尘、12 个月校准 |
| 弄一下 | `[]` + 反问 | 正确反问，不兜底动手 |
| 这个月电费多少 | `energy` | 10 条事实，峰谷占比分析 |

#### 12.19.3 验收

- `tests/agent_check.py`：**59 PASS / 0 FAIL**（新增 5 条路由兜底规则单测，不调模型、零额度成本）
- 高风险红线在真实模型下依然成立：scene + security 双 Agent 并行时门锁触发
  `interrupt()`，`中断=True`，全库无自动执行记录。

### 12.20 数据时间轴修复：模拟数据跑到了"未来" —— **完成**（v1.18 新增）

#### 12.20.1 现象与根因

界面上到处是未来时间，Agent 回答里出现：

```
数据更新于 2026-10-18T07:55，而当前时间为 2026-10-15 19:54，该数据已过期（未来时间）
```

实测 `device_readings` 共 472,591 行，其中 **470,706 行是未来数据（99.6%）**。

两层根因：

1. 按倍速跑满 24 小时（`--speed 30 --duration 1440`）后，模拟时间冲到 `now + 24h`；
2. `--start auto` 的续跑规则是"库里最新 ≥ 当前时刻就从它之后接着跑"
   （这条规则本意是防止时间轴**回退**），结果变成**越跑越超前，再也回不来**。

#### 12.20.2 修复

| 改动 | 说明 |
|---|---|
| 新增 `--start back:<分钟>` | 起点 = 当前时刻往前 N 分钟；配合相等的 `--duration N`，**终点正好落在现在** |
| 启动日志打印"模拟终点" | 并标注 `✅ 不晚于当前时刻` / `⚠️ 晚于当前时刻（界面会出现未来时间）` |
| 清理历史脏数据 | `DELETE ... WHERE observed_at / started_at > now`，共删除 **506,207 行** |
| 重新补历史 | `--start back:1440 --duration 1440 --speed 600` |

推荐用法写进了 `publisher.py` 的模块文档：

```bash
python -m gateway.simulator.publisher --start back:1440 --duration 1440 --speed 600
```

#### 12.20.3 验证结果

重跑耗时 **207.5 秒**（加速比 416x，累计发布 552,919 条）：

| 表 | 行数 | 未来数据 | 最新时间 |
|---|---|---|---|
| `device_readings` | 900,430 | **0** | 2026-10-15 20:05:07 |
| `energy_readings` | 68,687 | **0** | 2026-10-15 20:05:07 |

- `data_anchor = 2026-10-15T20:05:07`，≈ 当前时刻；32 台设备全部在线
- 按小时分布均匀（每小时 3.6~4 万行），完整覆盖 10-14 20:00 → 10-15 20:05
- 对话复验：「客厅现在多少度」→ `scene`，9.8s，
  「客厅当前温度 28.24℃，湿度 57.3%（**数据更新于 20:05，距今约 6 分钟**）」——不再出现未来时间

⚠️ 观察经验：生成结束后**落库还会持续几分钟**（后端消费积压），此时查 `MAX(observed_at)`
会得到"处理中"的偏早值，容易误判成丢数据。应**按小时分组**看整体分布，
或等"最近 1 分钟新增为 0"再下结论。

#### 12.20.4 操作顺序（实测踩坑）

Mosquitto **不是 Windows 服务**，每次开机都要手动启动；且**后端必须在 broker 之后启动**
才能建立订阅（先启后端会连不上，表现为 `health.mqtt.connected=false`、数据不落库）。

正确顺序：**启 broker → 启后端 → 跑生成器**。

### 12.21 控制指令闭环修复 —— **完成**（v1.18 新增）

#### 12.21.1 问题

用户实测反馈：发出「打开玄关灯」后对话显示完成，**设备依旧显示关**。
要求：不能全是写死的历史假数据，用户发指令后数据必须变（开空调要慢慢降温）。

#### 12.21.2 根因（四层）

| # | 根因 | 表现 |
|---|---|---|
| 1 | 模拟器跑完批量历史就退出，MQTT 上没人接收 `cmd` | 指令石沉大海（**主因**） |
| 2 | `apply_command` 覆盖有 TTL 60 模拟分钟 | 60 倍速下 1 真实分钟就失效："刚开的灯自己关了" |
| 3 | 模拟器状态只在内存 | 重启一次，之前开的灯全灭 |
| 4 | 后端没订阅 `cmd_ack` | 不管设备有没有变，回答都写死"已完成 N 个动作" |

#### 12.21.3 修复

| # | 改动 | 文件 |
|---|---|---|
| 1 | 新增 `--max-ahead N`：倍速演化但模拟时间最多领先真实 N 分钟，超过就暂停推进（每次只睡 1 秒，指令回调不受影响） | `publisher.py` |
| 2 | `apply_command(ttl_min=None)` 默认**持久**；未登记 `override_until` 即持久 | `physics.py` |
| 3 | 新增 `load_last_commands()`：启动时重放 `status='executed'` 的最后状态，**`pending_confirm` 永不重放**（红线不因重启被绕过） | `registry.py` / `publisher.py` |
| 4 | 订阅端分流 `/cmd_ack` → 回执写进 `device_commands.result_message` | `subscriber.py` |
| 5 | 回答措辞改为「已向 N 个设备下发指令（…），设备回报后状态即可见」——**下发成功 ≠ 设备状态已变**，不许谎报 | `nodes.py` |
| 6 | 新增 `scripts/start_dev.py` 一键启动 | `scripts/` |

#### 12.21.4 正确用法

```bash
# 一次性：补 24 小时历史（终点落在现在）
python -m gateway.simulator.publisher --start back:1440 --duration 1440 --speed 600

# 常驻：实时演化 + 超前上限（指令才有人接收）
python -m gateway.simulator.publisher --start auto --speed 60 --duration 0 --max-ahead 3

# 或者一条命令全搞定
python scripts/start_dev.py --backfill
```

#### 12.21.5 实测

- 开灯：30 秒内 `power_on` false→true，**2 分钟后仍为 true**（旧 TTL 下 1 分钟就失效）
- 关灯回执：`[回执] 设备已确认：✅power_on=false（已应用…持续生效，直到下一条指令）`
- 空调：设 18 度后室温持续下降（21.66 → 21.57 → …），走的是制冷曲线
- `data_anchor` 始终卡在真实时间 +3 分钟内
- 重启模拟器后按数据库最后一条 executed 指令恢复状态

#### 12.21.6 两个坑

- `apply_command` 返回文案里的 `{ttl_min:.0f}` 在 `ttl_min=None` 时抛 `TypeError`，
  导致模拟器启动即崩溃 —— 改默认值为 None 时必须同步改返回值格式化。
- 空调**只制冷**：室温 21.66℃ 时设 26 度不会制冷。演示降温必须把目标温度设到
  **当前室温以下**。
