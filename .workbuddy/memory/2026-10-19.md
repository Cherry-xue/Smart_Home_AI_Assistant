# 2026-10-19 · 套房增删 UI + 设备页白屏修复

## 一、设备页"完全打不开"的真因（白屏）

`frontend/dashboard-v2/src/pages/devices/index.vue` 里用了 `useHomeStore()`，
但**没有 import**。组件 setup 阶段直接抛 `ReferenceError`，整个页面白屏。

根源是上一轮多套房改造时用脚本批量插入 import：匹配串写的是
`import { ElMessage } from 'element-plus'`，而设备页实际是
`import { ElMessage, ElMessageBox } from 'element-plus'`，`str.replace` **静默没匹配上**，
但紧接着的 `const home = useHomeStore()` 却插进去了。构建不报错、运行时才炸。

**教训：批量脚本改完必须逐个核对"用到的符号都有 import"**，例如：

```bash
for f in src/pages/*/index.vue; do
  echo "$f 用=$(grep -c 'useHomeStore()' $f) 导入=$(grep -c 'import { useHomeStore }' $f)"
done
```

## 二、套房的新建 / 删除

后端：

- `backend/app/services/homes_admin.py`
  - `create_home(db, name, room_names, timezone)`：名字去空白、重名 409、房间 1~12 个且不许重名；
    **房间编码由后端生成 `room_1…room_n`**（编码进 MQTT topic，不能让用户输入 `/ + #`）。
  - `delete_home(db, home_id)`：级联删除，禁止删最后一套房。
- `backend/app/api/homes.py`：`POST /api/homes`、`DELETE /api/homes/{id}?confirm=true`
  - 删除必须带 `confirm=true`，否则 400（防误拼 URL 直接删库）
  - 删除/新建后都 `_reload_catalog()`，**就地 refresh 不换对象**（采集器持有同一引用）

⚠️ **级联删除用批量语句，不要按设备循环**：
`DELETE FROM device_readings WHERE device_id IN (SELECT id FROM devices WHERE home_id=:h)`。
1 号房 328 万行读数，逐台 32 条 DELETE 会让请求卡几分钟，界面像"点了没反应"。

⚠️ **删除过程中不要 kill 后端**：这次实测 kill 掉正在跑的大事务，MySQL 回滚要几分钟，
期间 `device_readings` 被锁 → 后续 INSERT 报 `1205 Lock wait timeout`，
并且 `app_rw` 没有 PROCESS 权限看不到 `INNODB_TRX`，只能用 `root` 看 PROCESSLIST 确认。

⚠️ 删除顺序（外键是 RESTRICT，没有 CASCADE）：
读数/事件/指令/能耗/能力 → 告警 → 场景运行 → 照护观察/偏好 → 用户角色 → 用户
→ 建议/记忆/对话/干扰规则 → 场景 → 成员 → 设备 → 房间 → 套房。
成员必须在用户之后删（`users.member_id` 指向成员）。

前端：

- `stores/home.js`：`add(name, rooms)`（建完自动切过去）、`remove(id)`
- `layout/AppShell.vue`：顶栏切换器右边加「＋ 新建」「删除」
  - 新建弹窗：套房名 + 房间行编辑器（默认客厅/主卧，最多 12 行）
  - 删除前 `ElMessageBox.confirm` 报出设备数/房间数；删除期间常驻一条 `duration: 0` 的提示
- `api/http.js` 新增 `del()`；`api/index.js` 新增 `createHome` / `deleteHome`

## 六、户型编辑器与命名分工（第二轮改动）

1. **框上直接显示房间名**：每个框左上角画一个蓝底白字标签（未指派的显示"未指定房间"、橙色底）。

   建完 emit `rooms-changed` 让总览页重拉房间列表。

4. **淡入淡出**：`styles/transitions.css` 原来只写 `.page-enter-from .page-fade`（后代选择器），
   而设备/照护/能耗页是把 `page-fade` 挂在**根节点**上 —— 过渡类也加在根节点，
   后代选择器永远不匹配，所以这些页一直没有动画。
   补了根节点版本 `.page-enter-from.page-fade`（无空格），两种挂法都支持。
   实测：切到设备页 opacity 从 0 → 0.28 → … → 1。

## 十二、删框即删房 + 空调指令排查 + 控件改下拉

1. **删框 = 删房间 + 设备 + 历史**：
   - 后端 `DELETE /api/homes/{hid}/rooms/{code}?confirm=true`（`delete_room`）：
     按 `device_child_tables()` 清掉 6 张设备子表（读数/事件/指令/能耗/能力/告警），
     再删设备与房间；房间维度的孤儿告警也清。
   - 编辑器点「删除」→ 确认框写明「房间 + N 台设备 + 历史数据」→ **保存时才真删**
     （`pendingDeletes`），取消编辑什么都不会删。
   - 顺序：**先存几何、再删房间**。反过来的话本次提交的几何还引用着已删房间，校验直接 400。
   - 删到最后一个框也要能保存：后端放开 `areas: []`（空户型合法），前端只在

2. **空调指令"没反应"的真相**：
   - 后端/MQTT/生成器链路是通的（实测 `mode=cool` → 6 秒内 `acknowledged=true`）。

## 十三、"图上没有这些房间"提示的含义与两个误报

用户看到「未画出的房间：卧室（它们的设备不会显示）」问这是什么。

来源：后端 `load_floorplan()` 算的 `missing_rooms` —— `rooms` 表里有、但户型 `areas` 里没有任何框指向它。
他那套「测试」房有 5 个房间（客厅/卧室/玄关/主卧/次卧），图上画了玄关、客厅、主卧、次卧 + 走廊，
**「卧室」是新建套房时自动生成的占位房间**（`DEFAULT_ROOM_NAMES`，0 台设备），
他画卧室时写的是「主卧」「次卧」，占位那个就一直没被用上 → 永久提示。

真问题：**没有框的房间在编辑列表里没有对应行，点不到删除** —— 只能被永久提示，是死胡同。

修法：
1. 提示改成 `图上没有这些房间：卧室 [移除]`，每个房间带「移除」按钮
   （`removeMissingRoom()` → 确认后 `DELETE /api/homes/{hid}/rooms/{code}?confirm=true`，
   有设备时确认框写明"N 台设备会一起删"）。
2. 修两处误报：
   - 只写了名字、**还没保存**的框按名字也算"已画出"（以前只认 `code`，保存前一直误报）；
   - 已标记 `pendingDeletes` 的房间不再提示（刚删了框还说"没画出"很像在催）。
3. 新建套房弹窗文案修正：之前写"客厅/主卧/次卧 三个房间 + 点＋新增房间"（早就过期的描述），
   改成"客厅/卧室 两个占位房间，可在顶栏「编辑」里改名或移除"。

实测（临时房 43，已删）：初始提示客厅+卧室 → 画框写「客厅」未保存即只剩卧室 → 点移除确认删除 → 提示消失。
`floorplan_check` 49 PASS / 0 FAIL。用户那套「测试」房**只读查看，未做任何修改**。


## 十四、新建套房不再默认建房间（+ 一个被它暴露出来的串台 bug）

用户要求：新建套房不要再自动生成两个房间。

1. `DEFAULT_ROOM_NAMES` 改成 `()`，`_clean_rooms()` 去掉"至少要有一个房间"的 400，
   所以 `POST /api/homes` 只传名字就会建出 0 房间的空套房。
   建房返回文案按有无房间分两种说法。

⚠️ **暴露出来的真 bug**：`GET /api/homes/{id}/rooms` 原来对"没有房间"也返回 404，

   - 后端：只有套房不存在才 404；存在但没房间 → 200 + 空列表。
   - 前端 `loadAll()`：五个请求**各自 `.catch()` 兜底**，一个接口坏了不再拖垮整页。

## 十五、户型图缩放（放大/缩小/还原）+ 「清空框选」到底是什么

用户要三键缩放，并问「清空框选」为什么点不了。

**根因**：那个按钮 `:disabled="!background"` —— 只有上传过底图才能点；
而且它干的是 `resetFloorplan(keep_background=true)`，即"把户型重置成默认（1 号房内置 8 间 /
其他套房为空），只保留底图"，跟名字"清空框选"不是一回事。

改法：
1. 新增 **`baseBox`（画布本体）与 `viewBox`（当前视口）两个状态**。
   ⚠️ 保存时必须写 `baseBox` —— 用视口会把"放大后看到的那块"存成画布，下次打开整个户型被裁。
2. 缩放：`ZOOM_MIN=0.4 / ZOOM_MAX=6 / STEP=1.25`，按钮以视口中心为锚、
   **滚轮**以鼠标位置为锚；`clampView()` 保证视口贴住画布（缩得比画布还小时居中留白）。
3. 平移：**中键拖动**（`panning` 状态 + `getScreenCTM().a` 换算像素→用户单位）。
4. 底图 `<image>` 与命中 `<rect>` 改用 `baseBox`（用 viewBox 会把底图拉伸到放大后的那块）。
5. 手柄尺寸 `HANDLE / zoom` —— 放大后手柄不会大得挡住框；标签字号用 `viewBox.w` 自适应，天然恒定。
6. 拖框/改大小的边界从 `viewBox` 改成 `baseBox`（否则放大后被夹在视口里、缩小后能拖到画布外）；
   画新框时夹到画布内，点在画布外留白不起手。
7. 「清空框选」改名 **「清空所有框」**：`disabled = !areas.length`，本地清空 + 二次确认，
   **不删房间、不动底图、不改画布尺寸**（房间留在底部「图上没有的房间」里可逐个移除）。
   `resetKeepBg()` 已删除（不再有调用方）；「恢复默认」保留原语义（连底图一起重置）。
8. 工具条提示压到一行（原来两行把画布压小了），缩放/平移提示挪到页脚。

实测（临时房 52，已删）：900×600 布局 → 放大 125%/156% → 框坐标不变 →
**156% 下保存，后端仍是 900×600**；手柄 12 → 6.14（视觉恒定）；滚轮生效；40% 触底禁用；
缩小后点画布外留白不产生框；还原 100%。`floorplan_check` 49 / `homes_check` 67，0 FAIL。

### 切页动效扩了一个方向：`.page-slide-right`

## 修「无法批准」（AI 对话页高风险卡片点批准报 404）

**根因**：`runner.stream()` 是 SSE 走的那条路。它在 `astream` 循环里遇到
`node == "__interrupt__"` 时**只 yield 事件，没有 `register_pending()`**。
而中断结束时那句 `_normalize(values)` 拿的是 `snapshot.values` ——
`__interrupt__` **不在 values 里**，所以 `interrupted` 恒为 False，会话永远进不了
待确认索引 `_PENDING`。结果：前端卡片画得出来（interrupt 事件有载荷），
点「批准」时 `/confirmations/{thread}` 查不到记录 → 404「该会话没有待确认事项」。
非流式的 `/api/chat`（`runner.run`）一直有登记，所以只有大屏的流式路径会挂。

**修法**：`backend/app/agent/runner.py` 的 `stream()` 里用局部变量 `interrupt_payload`
抓住流里的中断载荷，收尾时优先用它：置 `out["interrupted"]=True`、回填 `intervention`、
`register_pending`。

**顺带修的两个隐患**：
1. **多套房串台**：待确认索引只记了 `question`，没记套房。已给 `register_pending` 的
   extra 加 `home_id`，`InterventionOut` 新增 `home_id` 字段，`confirmations.list_pending`
   透传；前端（chat 页侧栏 + AppShell 消息抽屉）按当前套房过滤（`home_id == null` 的老数据照显示）。
2. **`intervention_index` 错位**：侧栏/抽屉是**跨会话扁平展开**的，而 index 是「同一会话内」
   的第几条。原来直接用列表下标（AppShell 更粗暴：恒传 0），多会话混合就会指错人 → 后端 400 越界。
   已改成按 `thread_id` 分组重新编号（`uiIndex`）。

**验收**（改完必须重启后端才生效，Uvicorn `--no-reload`）：
- 流式问「帮我把入户门锁锁上」→ `/confirmations/pending` 查到 1 条（带 home_id=1）→ 批准 accepted=true
- 再问「把燃气阀关掉」→ 驳回 accepted=true，列表归零
- `agent_check` 63 PASS（新增 4 条断言：final 标记 interrupted / 带载荷 / 进索引 / 载荷有 interventions）
- `api_check` 72 PASS、`homes_check` 67、`floorplan_check` 57、`m6_check` 59 全绿
- `npm run build` 通过

⚠️ 教训（第二条同类）：**流式路径和非流式路径要同步维护状态**。
`runner.run` 有的收尾逻辑（登记/清理 pending），`runner.stream` 也必须有，
但流式拿不到中断载荷（只存在于流事件里）—— 这类"只在一条路上能拿到的数据"，
写第二条路时最容易漏。给 `stream` 补的断言已经钉住这点。

## 执行过程条（AI 对话页）统一底色 + 加边框

### 更正：上面那条「height: auto」是错的，标题错位的真凶是 min-height

`element-plus@2.9` 的 `.el-collapse-item__header` 用的是
`min-height: var(--el-collapse-header-height)`（48px），**不是 `height`**。
只写 `height: auto` 完全压不下来 —— 标题被摁在 48px 的盒子里垂直居中，
于是和左边「已完成 N 步」错开一大截（截图里就是那个德行）。
正确写法：`height: 20px; min-height: 20px; line-height: 20px; padding: 0;`。
⚠️ 教训：改第三方组件高度前先 `grep` 它的 dist/index.css 看是 `height` 还是 `min-height`，
别凭印象写 `height: auto`。

### 再更正：错位真正的原因是 `.el-collapse-item__title` 这个包装层

`#title` 插槽**不是** header 的直接子节点 —— Element 会再包一层
`.el-collapse-item__title { text-align:left; flex:auto; order:1 }`。
这层是行内排版，两段字号不同（13px / 12px）的文字共用基线 → 视觉上"底部对齐"，
用户要的"中线对齐"出不来。

正解：把插槽里的两段文字**都塞进 `#title`**，再给 `.el-collapse-item__title`
加 `display:flex; align-items:center; gap:8px;`（`:deep()`）。这样两个 span 变成
flex item，中心线天然对齐，也不用两头各算一遍行高。

⚠️ 教训：Element 的插槽经常有隐藏包装层，改布局前先
`grep -o "el-collapse-item__[a-z]*" node_modules/element-plus/dist/index.css` 看真实 DOM 结构。

## 修「窄房间读数溢出」（"明明别的房子不会这样，不是一套逻辑吗"）

**不是两套逻辑，是一套逻辑漏了单位换算。**
`FloorPlan.vue::dataLineFor` 里 `avail = (a.w - 16) / 11`：`a.w` 是 **viewBox 用户坐标**，
`11` 是**屏幕像素字号**，中间差一个 `planScale`。

- 77 号房：`viewBox` = 底图原图像素 2358×1668，容器 760px → 缩放 **0.32**；
  阳台 w=223 用户单位 → 屏幕上只有 72px，真实只能放 5.3 字宽，旧算法算出 18.8 → 硬塞两个指标 → 文字压出边框。
- 2 号房：手绘坐标 900×600，缩放 ≈0.84 → 缩放比接近 1，旧算法"恰好"对，所以看着正常。

**修法**（`pages/overview/FloorPlan.vue`）：
1. 新增 `availUnits(a) = (a.w * planScale - 14) / 11`（左右各 7 屏幕像素内边距），
   不再用 `avail >= 11 ? 2 : 1` 拍脑袋，改成**按真实拼接文本长度判**：
   两条放得下就两条 → 否则一条 → 连一条都放不下就只留数值（阳台这种窄条）。
2. 删掉 `fitText`（截成「亮度…」既占地方又没信息量）。
3. `onMounted` 里先**同步** `measure()` 一次再挂 ResizeObserver —— 否则首帧 planScale
   还是初始值 1，带底图的户型会先按"很宽"画两条、下一帧再跳回一条，肉眼闪一下。

**实测（容器 760×600）**：77 阳台 72px → 「亮度 81 %」；2 号房书房 697px → 「温度 30.9 ℃ · 湿度 55 %」。
⚠️ 教训：SVG 里**用户坐标和屏幕像素混用**，任何"按宽度决定排版"的地方都必须过 `planScale`；
   而且这种 bug 只在某几种屋型下暴露（底图 vs 手绘），最容易被当成"两套逻辑"。

## 灯具亮度三连修：调光太慢 / 关灯还显示亮度 / 亮度随机跳

用户三条诉求 → 四处改动：

**① 调光只能加减、每次等回信** —— `components/DeviceControls.vue` 的数值型能力
从「− 值 +」步进按钮换成 **el-slider（松手才发一条）+ el-input-number（回车/失焦才发一条，
`controls="false"` 刻意去掉箭头）**。以前 20→80 要发 12 条指令、等 12 次回报。
难点是**红线冲突**：项目规定"只有真改了值才能说改了值"，不能乐观更新设备值；
但滑块松手后弹回原值又像"没生效"。解法是**本地期望值 `wish`（reactive）**：
拖动/输入只改 `wish`，回执到了（或等满 12s 判定无回执）`delete wish[cap]` 换回真实值；
下发失败/被拦下时也在 finally 里清掉。

**② 灯关了还显示"亮度 66 %"** —— 真凶是 **LatestValueCache 存的是"每个指标最后一次上报值"**：
灯关后模拟器不再上报 brightness，缓存里还留着关灯前的值（实测差 6 分钟）。
修在后端 `services/overview.py`：新增 `OFF_MEANS_NO_VALUE = {"brightness": "power_on"}`，
组装房间 key_metrics 时，若该设备的开关量**明确上报为关**就丢弃该指标
（没上报过开关量就不猜，避免刚上线的设备整块消失）。
⚠️ 修在后端而不是前端：户型图 / 房间卡片 / 右侧数据面板三处都要一致。

**③ 亮度随机跳** —— `gateway/simulator/physics.py` 的灯分支原来是
每帧 `rng.randint(lo, hi)`。改成：① 有调光指令 → 用 `manual_overrides` 的值（持久）；
② 没有 → 首次采样定一次存进 `self._steady_brightness`，之后恒定。
随机跳变的坏处是"刚调成 35%，下一秒跳回 72%"，用户判断不出指令到底生效没有。
（tv/speaker 的 volume 也是同样的随机跳变，**暂未改**，用户没提。）

**④ 文案** —— `utils/format.js` 的 `METRIC_LABEL.brightness` 从「亮度」改「环境亮度」：
房间读数表示的是"这间房现在有多亮"，叫「亮度」会被当成灯具档位，于是出现
"灯关着却显示亮度"的误解。设备面板里能力档案自带的 display_name「亮度」不动（那是可调项）。

**实测**：关灯后 77 阳台 key_metrics 只剩 power_on=False；开灯后 brightness=65 出现；
下发 brightness=35 后连续 3 次采样恒为 35；1 号房玄关/阳台亮度连续 3 次采样恒为 40/43。
`api_check` 72、`m6_check` 54、`homes_check` 67 全绿；`npm run build` 通过。
（改了后端与模拟器 → 两个进程都重启过）

### 补：音量也改成稳定值（与亮度共用一套）

`gateway/simulator/physics.py`：把灯亮度的专用字典 `_steady_brightness` 泛化成
`_steady_values: dict[(device_code, capability), object]`，并抽出通用方法
`_steady_value(dev, capability, now, gen)` —— ① 有指令用指令值；② 否则首次调 `gen()`
定一次、之后恒定。`gen` 传 lambda 惰性求值，避免每次采样白耗一次随机数。
tv / speaker 的 `volume` 都改走它（原来和 brightness 一样是每帧 `rng.randint`）。
实测重启后三次采样：客厅电视 27、智能音箱 32，恒定。

窗帘 `position` 的 ±3 抖动**故意保留** —— 它是"按时间段的开合度 + 轻微漂移"，
不是用户设定的档位；空调 `target_temp` 本来就不是随机的。

⚠️ 用户视角的"还有一个你没改"：亮度调光其实上一轮就从「±5 步进按钮」换成了
「滑杆（松手才发一条）+ 手输框」，但他看到的是**没刷新的旧页面**
（dev 5174 返回的模块里已含新 class `num-slider`/`num-input`，已核实）。
旧界面让人觉得"点一下要等几秒"的真因是**界面不做乐观更新**（红线），
数字要等设备回执才变；新控件拖动/输入时先显示本地期望值 `wish`，回执到了再换回真实值。

## 人工确认闭环：从"只留痕"改成"批准即执行"（红线口径细化，用户拍板）

用户反馈两件事：① 面板提示"已生成待确认项"但**消息抽屉里什么都没有**；
② 质疑"人工确认了状态也不变，那确认不就是摆设吗"。

**根因**：
- ① 手动控制只写了 `device_commands`（pending_confirm），**没登记 `_PENDING`**，
    而消息抽屉读的是 `_PENDING` —— 生成了却没人能处理。
- ② 旧实现里批准只写 `confirmed_at`，`_settle_high_risk` 明确注释"真正的动作需人到现场"，
    在模拟环境里"现场"不存在，确认确实是摆设。

**改动**（红线从"永不执行"精确成"**绝不自动执行，人工授权后才执行**"）：
1. `services/scenes/executor.py` 新增 `dispatch_confirmed()` —— 全链路**唯一**允许
   高风险设备动起来的函数。状态链 `pending_confirm → confirmed → executed`，
   中间那次 commit 是留痕（发不出去时能看出"人批了但没发出去"）。
2. `services/device_control.py`：pending 时 `register_pending("manual-cmd-{id}")`，
   载荷结构与 Agent 中断一致（列表/卡片不用两套渲染）；新增 `_expire_stale_manual()`
   —— 连点三次解锁只留最新一张待办，旧的标 expired（**只动 source=dashboard 的行**，
   不能碰 Agent 的，否则库里和内存中断索引对不上）。
3. `api/confirmations.py`：`decide()` 遇到 `manual-cmd-` 前缀走下发分支（不 resume 会话）；
   `list_pending` 加 **DB 兜底**（`_PENDING` 是内存，重启就丢），只捞 24h 内、
   同设备同能力只留最新。已处理过的状态直接拒绝重复执行。
4. `agent/nodes.py::_settle_high_risk`：批准后调 `dispatch_confirmed`（原来只留痕）。
5. 文案全面改口径：面板"高风险设备 - 需要手动确认"、消息抽屉按钮"批准并下发"、
   "⚠️ 只有你批准才会真正下发一次"。

**踩坑**：prompt 别拼 `{room_name}{device.name}` —— 设备名本身带房间，会成"厨房厨房燃气阀"。

**验收**：下发解锁 → 列表出现 `manual-cmd-485`（历史重复项已收敛）→ 批准 →
门锁实测 `locked → unlocked`（20:22:44 上报）→ 列表归零；驳回门锁后状态保持 unlocked 未执行；
复位 locked 成功。`agent_check` 62 PASS（含"批准后真的下发 executed=1"与
"凡执行必有 confirmed_at"全库校验）、`api_check` 72、`m6_check` 54、`npm run build` 通过。
