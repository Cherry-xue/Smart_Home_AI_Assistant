## 13:50~14:25 启动整套系统（用户要照现有前端设计新前端）

### 🔴 修掉一个真 bug：`start_dev.py` 的启动顺序会**静默丢数据**

原脚本顺序是 `broker → 补历史 → 后端 → 常驻模拟器`，**补历史排在后端之前**。
但生成器（`gateway/`）**整个目录没有任何写库代码**，唯一入库通道是后端订阅者
（`app/mqtt/ingest.py` 的 `insert(DeviceReading)` 等）。所以冷启动时补历史 =
消息发进空 MQTT、无人接收、**全部丢失**。

**实测证据（不靠推理）**：后端未起时补 3 分钟，生成器报"累计发布 1155 条"且**正常退出**，
但 `device_readings` 行数 **925,750 → 925,750 完全不变**。这个坑的阴险之处是
**生成器会成功退出并打印发布条数**，光看日志像是成功了。

**修法**：把补历史移到后端之后（新顺序 `broker → 后端 → 补历史 → 常驻模拟器`），
并加 `_ingest_readings()` 读 `/api/health` 的 `ingest.readings`（进程内累计计数）
做前后核对，增量为 0 就 `return 1` 报错 —— 把"悄悄丢数据"变成"当场报错"。

## 15:43~16:00 页面切换动效（下方菜单升降 + 主显示区淡入淡出）

用户要求：切页时**下方菜单下沉到界面外**；新页面若也有下方菜单则**从屏幕下方升起**；
**主显示区淡入淡出**。

### 实现：三段配合
1. **过渡外壳**（`layout/AppShell.vue`）：
   `<RouterView v-slot>` + `<Transition name="page" mode="out-in" :duration="{enter:400,leave:280}">`
   `mode="out-in"` 保证"下沉 → 升起"是两段，不会两页抢位置。
   另给 `.main` 加 `overflow: hidden` —— 下方菜单要能滑出可视区并被裁掉。
2. **页面钩子类**（各页面自己标）：
   · `.page-fade` —— 主显示区，淡入淡出
   · `.page-slide` —— 下方菜单，升降（**没有下方菜单的页面不标，就不会有升降**）
   已标：overview 的 `.stage`(fade) + `.bottom`(slide)、devices 的 `.page`(fade)、Placeholder 的 `.ph`(fade)
   用**语义钩子**而不是 `.stage`/`.bottom`，是为了让全局过渡样式与页面 scoped 布局解耦。
3. **过渡样式**：新文件 `styles/transitions.css`（main.js 里引入）

### 🔴 核心坑：Vue 只看**根元素**的过渡时长
第一版写完实测**动画完全没播**：点完导航，旧页面已经没了（eval 显示 `stage 已卸载`）。

根因：`<Transition>` 判断"离场结束了吗"的办法是**读根元素的 computed transition 时长**，
而我们的过渡挂在**子元素**（`.page-fade` / `.page-slide`）上，根元素自己没有过渡
→ Vue 认为瞬间结束 → 立刻卸载旧页面 → 子元素的动画跟着一起被带走。

**修法：给 `<Transition>` 显式传 `:duration="{ enter, leave }"`**（官方就是为这种场景准备的）。
⚠️ 改 `transitions.css` 里的时长时，**这两个数要同步改**。

### 沉淀的验证手法（很有用，比截图精确）
**在页面内用 JS 采样过渡过程**：`eval` 里返回一个 `Promise`，内部 `setInterval` 每 60~70ms
记一次 `getComputedStyle`，1 秒后 resolve 出整条时间序列。
- 比截图精确得多，能直接看到插值过程
- 而且**当 `:duration` 让"慢放"失效时**（Vue 按固定毫秒等待，放大 CSS 时长没用），它是唯一可行的办法

### 实测时间序列（两个方向都验了）
设备页 → 总览页（下方菜单升起）：
```

422ms  opacity=0.16  TY=94.6      ← 淡入与升起同时进行
495ms  opacity=0.73  TY=33.0
634ms  opacity=0.99  TY=2.63
701ms  opacity=1.00  TY=0.04      ← 到位
```

## 16:12 评估两个新想法（**只做了调研，未开工**）

用户提了两个想法要评估可行性：
①支持上传指定样式的户型图，据其改变前端界面；
②支持手动添加/删除设备，提供预设设备（他估计"要大改生成器"）。

### 🔍 调研结论（都是实测/读代码得来的，不是印象）

**① 户型图现状：几何是写死的**
- `rooms` 表**没有任何几何字段**（只有 id/home_id/code/name/floor/sort_no/created_at）
- 几何只存在于 `frontend/dashboard-v2/src/pages/overview/roomGeometry.js`（我写的数据 + 墙线生成算法）
- 渲染已经是**数据驱动**的（`AREAS` + `wallSegments()`），换几何不难

**② "大改生成器"其实**不需要**——这是最重要的结论**
- `devices.device_type` 是 **`varchar(48)` 不是 enum** → 加新类型**不需要 DDL**
- `device_capabilities` 有唯一键 `(device_id, capability_code)`，`device_capabilities.device_id` 是 **ON DELETE CASCADE**
- 物理档案按 **`device_type`** 索引（`device_types.get(dev.device_type, {})`）
  → **未知类型不崩**，只是没有物理模型（会退化成都市/静态数据）
- ⚠️ **但 `cfg["thermal_tau_min"]` 是直接索引** → **新房间会让生成器 KeyError 崩掉**（必须先修）

**③ 软删设备「已经能用」——重大发现**
`devices.enabled` 字段已存在，且**后端 catalog 与生成器 registry 都写了 `WHERE d.enabled = 1`**
→ `UPDATE devices SET enabled=0` 就能让设备从接口和生成器里同时消失，零改动。

**④ 硬删设备会被外键挡住**
`device_commands.device_id` 与 `sensor_events.device_id` 都是 **ON DELETE NO ACTION**
→ 删除报 1451。且 `device_readings`（167 万行）**没有指向 devices 的外键** → 硬删会留下大量孤儿行。

**⑤ 后端目录目前不热加载**
`app.state.catalog` 只在启动时 `DeviceCatalog.load(engine)` 赋一次，**没有 reload**
→ 运行时加的设备要重启才可见。（`load()` 是 classmethod，加重载端点是小改动）

**⑥ 生成器 registry 也只在启动时读一次**
`registry.py` 在启动时按 `WHERE d.enabled=1` 读设备；常驻进程不会自动发现新设备 → 需要周期性重扫。

### 我给出的建议（含红线）
- **`high_risk` 绝不能由用户设置**：否则用户加一个"门锁"类型设备、把 `high_risk` 填 0，
  就把"高风险永不自动执行"这条核心红线绕过去了。必须由**后端按设备类型推导**。
- 几何存储建议放**后端配置文件**（如 `config/floorplan.json`）而不是库里：
  避免 DDL（`app_rw` 无 DDL 权限，按约定 DDL 只能在虚拟机手工执行）
- "上传图片自动识别房间"**不现实**（是 CV 问题）；现实做法是
  **上传图片当底图 + 用户手动框选房间区域**（可让视觉模型给个初始猜测，用户再改）
- 建议先做②（改动小、解锁真实可用性），再做①
