### 建表的关键设计决定（已写进文档 §12.8）
1. **表/字段全写 COMMENT** —— 会被 LangChain `get_table_info()` 拼进提示词，提升模型读表准确率性价比最高的一招

3. **遥测按指标存（EAV）** —— `device_readings` 一行一个 metric，容纳"一条消息含多指标"的信封，加指标不用改表
4. **`device_capabilities` 防臆造核心表** —— 带 `value_min/value_max/enum_values/risk_level`
5. **高风险在数据层双重标记** —— `devices.high_risk` + `device_commands.status` **默认就是 `pending_confirm`**（默认不执行，而不是默认执行）

### ⚠️ 迭代中修掉的 5 个问题（3 个是物理建模错误，最有价值）
1. `KeyError: indoor_bias` —— 参数放错层级（在 `environment` 下却从 `indoor` 取）
2. **空调被当成"双向温控"** —— 出现"空调把房间加热到 27℃"的荒谬结论。
   实际上**空调只能制冷**：自然室温 24℃、设定值 27℃ 时它根本不该启动。
   → 新增 `natural_indoor()` / `ac_cooling_demand()`
3. **缺恒温器死区** —— 温度被精确停在设定值上，压缩机"制冷一次就再也不动"
   → 引入死区：超过设定值 0.3℃ 才启动、降到设定值就停
4. **制冷速率比吸热慢** —— 温度卡在死区上方降不下来，压缩机连续运转看不到启停
   → 显式设 `ac_cooling_tau_min: 5.0`（远快于吸热）
5. `gas_valve` 在指标函数里漏了处理 → 32 台设备只出 31 个 topic

### ⚠️ 三个坑（这部分最有价值）
**1. aiomqtt 在 Windows 默认事件循环上根本不工作**
- 症状：订阅服务始终 `connected=False`；报错堆栈落在 `paho/mqtt/client.py` 的 `__del__` 里，**看起来像可以忽略的垃圾回收噪声**，极易被放过
- 根因：aiomqtt 底层是 paho 的 asyncio 封装，用 `loop.add_writer()` 驱动 socket；**Windows 默认 ProactorEventLoop 的 `add_writer/remove_writer` 直接抛 `NotImplementedError`**
- 修法：`WindowsSelectorEventLoopPolicy`，且**必须在事件循环创建之前设置**
- **⚠️ M2 必须照做**：uvicorn 在 Windows 同样默认 Proactor → `app/main.py` 顶部要调 `ensure_selector_loop_on_windows()`，否则"接口正常、数据不进库"
**2. retained 快照污染时间基准 → 一轮 510 条被误标 stale**
- broker 在订阅瞬间回放 **22 条 retained** 消息（`state` 是 retained 的），其时间戳是**上一轮模拟到的"未来时刻"**（16:04）
- 它被当成"上一条"的时间基准 → 之后所有实时数据（14:09 起）全被判"时间倒退"，最新值缓存也从 32 台掉到 30
- 定位方式：`22 台 × 24 拍 ≈ 528`，与观察到的 510 吻合；并写了个探测脚本印证"新订阅者 2.5 秒内收到 22 条 retain=1、时间戳全是 16:04:10"
- 修法：retained **照常入库但单独计数、不参与时间基准判定**
**3. 生成器多轮运行导致时间轴回退**
- 每轮都从"当前时刻"硬开始，而库里 / broker 上已有更晚时间戳的数据
- 修法：`--start` 默认 `auto` = **max(库里最新数据, 当前时刻)** 之后续跑
- 实测日志："续跑：库里已有至 10-15 16:04:10 的数据，避免时间轴回退"

> 坑 2 与坑 3 是同一问题的两端：**消费方不该拿历史快照当时间基准，生产方不该让时间轴回退**。两边都修 → 双重保险。
> 这类"数据源时间轴"问题在真实 IoT 里很常见（设备时钟漂移、网关补发、重放历史），答辩讲这一条比讲"我们用了 MQTT"有分量。

### 四个关键技术决定
1. **订阅服务跑独立线程，不内嵌 FastAPI 循环** —— aiomqtt 要 Selector，uvicorn 在 Windows 用 Proactor，
   且"循环创建后不能改类型"→ 内嵌无干净解。独立线程自带循环（`--reload` 也能用）+ 同进程共享缓存。
   代价：缓存加 `RLock`。
2. **查库端点写 `def` 不写 `async def`** —— 同步 SQLAlchemy 直接跑在事件循环里会卡住整个后端；
   `def` 让 FastAPI 自动丢线程池。**本项目所有查库端点都适用这条。**
3. **⚠️ 两个缓存实例的坑（最隐蔽）**：`Ingestor.__init__` 自己 `new` 了一个 `LatestValueCache`，
   与 `app.state.cache` 不是同一个 → 一边写一边读。症状极具迷惑性：
   health 显示"MQTT 已连接、收到 1032 条、数据在入库"，但接口读到的**永远是预热值**、32 台设备全"离线"。
   **修法：缓存改为可注入，main 把 `app.state.cache` 传进 Ingestor。**
4. **缺省时间窗以「数据最新时间」为锚点**（`overview.data_anchor`，health 里暴露为 `data_anchor`）——
   模拟器按倍速跑，数据时间跑到真实时钟之外，用"现在往前 24h"**一条都查不到**。
   anchor ≈ now 时与旧行为完全等价。

### 三个时间语义（极易混，已写进代码注释）
| 概念 | 含义 | 用途 |
|---|---|---|
| `observed_at` | 设备报出的观测时间（可能不准/在未来/是补发） | 显示"值什么时候测的" |
| `received_at` | 我们实际收到消息的**本机时间** | **判断设备在线** |
| `last_observed_at` | 手上最新数据的观测时间（**含预热**） | 显示"数据更新时间" |

### ⚠️ 三个被修掉的语义错误（实测踩出来的）
1. **预热也算"在线"** → 库里数据时间戳很新 → MQTT 完全没连上、32 台设备却全显示"在线"
   → 修法：预热只填值，**不碰** `_last_seen_live`
2. **用 `observed_at` 判在线** → 设备时钟跑到未来 = "永远在线" → 改用 `received_at`
3. **retained 计入在线** → "broker 上存着它的最后状态"被当作"它现在在发数据" → `count_as_live=False`

### 实测结果（broker + 生成器 + API 三者同跑）
```
在线状态 : 32/32（7 个房间满员）        ← 修复前 0/32
实时值   : seq=35、last_seen=2026-10-15T14:58:01（本机接收时间）
缓存     : 32 台 / 61 个值（61 个来自启动预热）→ 重启后态势立刻可见
能耗汇总 : 6.1581 kWh ≈ ¥3.8813
           valley 3.2305 kWh → ¥1.1307（51.6% 电量 / 29.1% 费用）
           peak   1.2331 kWh → ¥1.4797（19.7% 电量 / 38.1% 费用）
```
→ **又出现"峰电用得更少、花得更多"**：这是分时电价的结构性事实，也是"挪到谷电"建议的量化依据。

### 核心设计一：冲突检测需要"可解释的判据"
最典型的冲突是**跨设备**的：「看电影」却把主灯开到 100% —— 它与氛围灯 30% 作用在不同设备上，
"同一设备同一能力被设两次"根本抓不到。

**解法**：给场景一个**意图模板**（YAML），声明合理区间（观影 `brightness≤40%`、`position≤30%`、`target_temp∈[24,27]`）。
超出即剔除，**原因写明判据**。实测输出：
```
被剔除：· 客厅主灯 brightness=100  ↳ 与「观影」场景冲突：观影场景需要环境偏暗，照明不宜超过 40%
        · 客厅窗帘 position=100  ↳ 与「观影」场景冲突：观影场景需要遮光，窗帘开合度不宜超过 30%
最终序列：氛围灯带 30 / 空调 24[clamped] / 电视 on / 音箱 on
```
→ **这正是规划书 §14.1 的验收要求"能复现被剔除的动作及原因"** ✓

### 核心设计二：编排顺序不能换
`能力校验 → 重复检测 → 意图约束 → 风险标记`
- 先校验再判重：否则拿"不存在的设备"互相比
- 判重放在意图约束前：先定"最终值"再看是否符合意图
- **风险标记放最后且不剔除**：剔除会让用户以为"系统不支持门锁"，实际是"支持但要确认"

### 核心设计三：执行三条归宿 + 一条不可降级的红线
| 情况 | 处理 | 落库 |
|---|---|---|
| 高风险（门锁/燃气阀/总闸） | 只生成待确认，**绝不执行** | `pending_confirm` |
| 普通设备 | 发 MQTT | `executed` |
| 失败（重试 3 次） | 记失败但**继续执行其余** | `failed` |

单步失败不中断整场（"音箱没连上"不该导致"灯也不开了"）→ `partial` + `fallback_used`。
⚠️ **不可降级的是高风险**：不靠调用方自觉 —— `executor.create_command()` 里有**强制掰回**的代码，
数据库默认值 `pending_confirm` 是第二道保险。**红线要写在代码里，不能只写在文档里。**

### 核心设计四：让"执行"真的有效果
原先生成器只发不收 → "执行场景"会变空壳（后端写了记录、发了 MQTT，设备纹丝不动，
演示时像"点了没反应"）。给生成器加了订阅与响应：
```
后端下发 cmd → 模拟器 apply_command → 后续 state 反映新状态 → 落库/进缓存 → API 立刻可见
```
两个细节：
1. **覆盖带 TTL（60 模拟分钟）** —— 真实设备手动控制后自动策略仍会接管；
   若永不过期，跑一晚上就"灯永远关着"，与作息模型脱节
2. **设备侧二次校验 + 回 ack** —— 真实设备不会因为"上游说合法"就照做；
   校验失败必须回 ack，否则后端会一直以为"发成功了"（比下发失败更糟）

### 端到端闭环实测（broker + 生成器 + API 同跑）
```
① 执行前 客厅主灯 {brightness:68, power_on:False}
② 执行   status=success executed=3（command_id 1/2/3）
③ 生成器 ✅ 收到指令 living_room_light_main.brightness=15 → 已应用
④ 执行后 {brightness:15, power_on:True}
⑤ 入库   最近6条 brightness = [92,50,51,68,15,15]
⑥ 复查   氛围灯带30 / 空调24 / 电视on / 音箱on 全部与指令一致
```

## M4 方案设计（已提出，待用户确认后开工）

用户问"你打算如何制作 5 个 agent"。先回查规划书 §4.1 / §9 / §13 确认基线，再实测 API。

### 术语对齐（重要）
规划书是 **1 个家庭协调 Agent + 5 个专业 Agent = 6 个**。用户说的"5 个 agent"指 5 个专业 Agent。
本方案：**协调 Agent = 主图上的路由节点**（不是独立子图），**5 个专业 Agent = 路由节点扇出后的并行节点**。

### ⚠️ API 实测结论（2026-10-15，勿凭记忆推翻）
1. **`langgraph.prebuilt.create_react_agent` 已带 `@deprecated(category=LangGraphDeprecatedSinceV10)`** —— 仍可导入但已弃用 → 规划书 §13.5 骨架确认过时
2. **`create_agent` 真实签名**（比规划书写的丰富得多）：
   `(model, tools, system_prompt, middleware, response_format, state_schema, context_schema, checkpointer, store, interrupt_before, interrupt_after, debug, name, cache, transformers)`
   - `response_format` → **结构化输出**（本方案关键）
   - `interrupt_before` / `interrupt_after` → 可在 Agent 内部打断
3. **`HumanInTheLoopMiddleware(interrupt_on={tool_name: bool|InterruptOnConfig}, *, description_prefix, edit_notice)`**
   `InterruptOnConfig` 字段：`allowed_decisions` / `description` / `args_schema` / **`when`（Callable[[ToolCallRequest], bool]）**
4. **`ToolCallLimitMiddleware(*, tool_name, thread_limit, run_limit, exit_behavior)`** / **`ModelCallLimitMiddleware(*, thread_limit, run_limit, exit_behavior)`**
5. `StateGraph.add_node(node, action, *, input_schema, retry_policy, cache_policy, error_handler, destinations, timeout, ...)`；`compile(checkpointer, *, store, interrupt_before, interrupt_after, name)`
6. `Send(node, arg)` 用于**并行 fan-out**；`interrupt(value, *, response_schema=)`；`Command(*, update, resume, goto)`
7. **`agent_runs` 表已为多 Agent 预留字段**：`route_agent` / `intent` / `tools_used` / `status`（含 `interrupted`）
   `conversations.thread_id` ↔ LangGraph checkpoint；`memories` 有 `source` / `confidence` / `decay_at` / `chroma_id`

### 架构方案
**一个主图**，5 个专业 Agent 是图上的节点（各自内部 `create_agent`，工具白名单物理隔离）：

```
提问 → router(LLM结构化分类) → Send 并行扇出 [5 节点] → aggregate(纯代码) → 确定性主干 → respond
```

**确定性主干复用 M3**（本方案最大红利）：`plan`（M3 planner：能力校验→冲突检测→意图约束）
→ `confirm_gate`（有高风险则 `interrupt()`）→ `execute`（M3 executor：重试/降级/高风险强制 pending）。

### 5 个 Agent 的工具白名单（关键：代码里的字面量，不靠 prompt 约束）
统一工具池（**都是 M1/M2/M3 已实现服务层的薄包装**）：
`read_device_state`(overview) · `list_capability`(catalog) · `read_history`(analytics) ·
`calc_energy_cost`(deterministic) · `search_knowledge`(rag) · `search_memory` · `read_recent_events` ·
`propose_actions`(→M3 planner) · `propose_notification` · `propose_suggestion`

| Agent | 工具白名单 |
|---|---|
| 1 场景编排 | read_device_state / list_capability / search_knowledge / propose_actions |
| 2 安防应急 | read_device_state / list_capability / read_recent_events / search_knowledge / propose_actions |
| 3 能源优化 | read_device_state / read_history / calc_energy_cost / search_knowledge |
| 4 健康照护 | read_device_state / read_history / read_recent_events / search_memory / propose_notification |
| 5 家务助理 | read_device_state / search_knowledge / search_memory / propose_suggestion |

⚠️ **任何 Agent 都没有"直接执行高风险动作"的工具** —— `propose_actions` 只产出建议，走主干才执行。

### 五个关键设计决定
1. **路由用 LLM，但走向必须是图上的边** —— 路由节点做一次结构化分类（输出 `RouteDecision`，落库 `agent_runs.route_agent`），
   之后走哪条边由图决定，不藏在模型的多轮推理里（可审计、可复现）
2. **并行 fan-out + `operator.add` reducer 合并** —— 混合题（"爸妈房间冷 + 顺便看电费"）care 与 energy 同时跑，
   wall-clock = 最慢者而非总和。⚠️ **并行分支里不能放 `interrupt()`**（LangGraph 已知限制）→ 所以 confirm_gate 必须在汇聚之后的主干上
3. **每个 Agent 必须输出统一结构化 `Finding`**（`response_format`）——
   含 summary / facts / analyses / proposed_actions / memory_refs / uncertainties / citations。
   否则汇总节点只能让模型"再总结一遍" = 信息二次损耗 + 幻觉风险。**汇总节点纯代码拼接，不需要模型**
4. **`interrupt()` 放在"计划级"而非"工具级"** —— 工具级中断是"每调一次高风险工具停一次"，多步任务体验破碎；
   计划级能一次性展示"整体要做什么 + 剔除了什么 + 为什么"（正好复用 M3 招牌演示）。`response_schema` 声明期望回复格式
5. **会话记忆 vs 长期记忆分开** —— 对话历史走 checkpoint（`thread_id` ↔ `conversations`）；
   长期偏好走 `memories` 表 + Chroma（`chroma_id` 关联），**只有置信度达标才参与个性化**

### 实施顺序（每步可独立验收）
1. 图骨架 + 路由 + **1 个 Agent**（场景编排，因 M3 就绪）打通全链路 → 验收"路由能选对、能跑通"
2. 确认链路（`interrupt()` / `Command(resume)`）+ SSE 流式 → 验收"高风险暂停/恢复、流式可见"
3. 补齐其余 4 个 Agent（骨架 + 结构化 Finding）→ 验收"5 个都能跑"
4. 并行 fan-out + 混合题 → 验收"多 Agent 协作"

### ⚠️ LangGraph 两个必须记住的坑
1. **`Command(resume=...)` 会重新执行被中断的节点**（这次 `interrupt()` 直接返回恢复值、不再暂停）
   → 节点里任何**写库动作必须幂等**。本项目 `confirm_gate` 落 `pending_confirm` 指令因此改成
   "按 thread_id + device + capability 复用已存在行"，否则批准一次就多一条待办。
2. **状态里的 Pydantic 模型必须登记序列化白名单** —— 否则每次反序列化警告
   `Deserializing unregistered type app.agent.models.X ... will be blocked in a future version`。
   已集中在 `app/agent/checkpoint.py` 的 `ALLOWED_MSGPACK_MODULES`（8 个类型）。**加新模型必须同步登记**。

### 设计决定（勿推翻）
- **执行分两段**：`execute_low`（低风险，中断前就跑掉）→ `confirm`(interrupt) → `execute_high`。
  理由：用户迟迟不确认时低风险已生效，才符合"其他直接执行，执行完告知"。
- **待确认指令在 interrupt 之前落库**，并把 `command_id` 回填到 `InterventionItem`；
  批准后是**更新那一行**（补 `confirmed_at`），不是新增。手机端待确认列表可从库重建，不依赖内存。
- **汇总 / 回答节点刻意不调模型**（结构化字段拼接，可测可复现）。
- checkpointer 默认 `memory`；`CHECKPOINT_BACKEND=mysql` 切 `PyMySQLSaver`（独立库 `smart_home_checkpoint`），失败自动退回内存。

### 验收脚本的两个自坑（已修）
- `runner.run()` 返回的键是 **`answer_sections`**（不是 `sections`）—— 取错会拿到空 dict，表现为"分区丢了"
- 断言"高风险未被执行"时**必须按 device_code 过滤**：`run_result` 是低风险+高风险合并的结果，
  broker 在线时 `executed` 里会有低风险动作，那是预期行为
- 测试用 thread_id 必须 **每次运行唯一**（加 `RUN_TAG`），否则幂等复用会命中上一轮遗留数据

## 20:14–20:40 指令闭环修复（用户实测发现："发指令后设备状态不变"）

**用户反馈**：发出"打开玄关灯"后对话显示完成，但设备依旧显示关。
要求：不能全是写死的历史假数据，**用户发指令后数据必须变**（开空调要慢慢降温）。

### 根因（一层套一层，共 4 个）
1. **模拟器跑完批量历史就退出** → MQTT 上没人接收 `cmd` → 指令石沉大海（主因）
2. `apply_command` 的覆盖有 **TTL 60 模拟分钟** → 60 倍速下 = 1 真实分钟就失效，
   表现为"刚开的灯自己关了""空调 target 从 18 跳回 26"
3. 模拟器状态只在内存 → **重启即丢**（重启后灯全灭）
4. 后端**没订阅 `cmd_ack`** → 不管设备有没有变，回答都写死"已完成 N 个动作"（谎报）

### 修复
| # | 改动 | 文件 |
|---|---|---|
| 1 | 新增 `--max-ahead N`（默认 5 分钟）：倍速演化但模拟时间最多领先真实 N 分钟，超过就暂停推进等真实时间追上（每次只睡 1 秒，指令回调不受影响） | `publisher.py` |
| 2 | `apply_command(ttl_min=None)` **默认持久**；`_active_override` 没登记 `override_until` = 持久 | `physics.py` |
| 3 | 新增 `registry.load_last_commands()`：启动时重放 `status='executed'` 的最后状态（**`pending_confirm` 永不重放**，红线不因重启被绕过） | `registry.py` / `publisher.py` |
| 4 | 订阅端分流 `/cmd_ack` → `_handle_cmd_ack()` 把回执写进 `device_commands.result_message` | `subscriber.py` |
| 5 | 回答措辞"已完成 N 个动作"→"**已向 N 个设备下发指令（…），设备回报后状态即可见**" | `nodes.py` |
| 6 | 新增 `scripts/start_dev.py` 一键启动（broker → 补历史 → 后端 → 常驻运行时），Ctrl+C 一次停全部 | `scripts/` |

### 正确用法（关键！）
```bash
# 一次性：补 24 小时历史（终点落在现在）
python -m gateway.simulator.publisher --start back:1440 --duration 1440 --speed 600
# 常驻：实时演化 + 超前上限，指令才有人接收
python -m gateway.simulator.publisher --start auto --speed 60 --duration 0 --max-ahead 3
# 或者一条命令：
python scripts/start_dev.py --backfill
```

### 实测（全部通过）
- 开灯：30 秒内 `power_on` false→true；**2 分钟后仍为 true**（旧 TTL 下 1 分钟就失效）
- 关灯：`[回执] 设备已确认：✅power_on=false（已应用…持续生效，直到下一条指令）` 落库
